# 文档管理规范

本规范用于约束仓库中的长期文档与智能体临时工作产物。目标是让项目知识保持少而可靠，避免随着自动化开发不断积累过时 Markdown，造成事实冲突和上下文污染。

## 1. `docs/` 的定位

`docs/` 只保存需要长期维护、未来开发者和智能体仍然需要参考的项目知识。

适合进入 `docs/` 的内容包括：

- 系统架构、架构边界和重要技术设计；
- 核心数据模型、API / 协议契约的设计说明；
- 核心业务流程、状态机和不可从源码快速推导的业务约束；
- 安全、认证和权限模型；
- 外部系统集成、部署、运维和故障恢复；
- 长期有效的架构决策；
- 项目特有、未来多个任务都会重复使用的开发者知识。

正式文档应随着代码变化持续维护，并被视为项目长期知识的一部分。

## 2. 长期知识晋升门槛

创建新的 `docs/*.md` 前，先回答：

> 六个月以后，一个不了解当前任务背景的开发者，为了正确理解、维护或修改当前系统，是否仍然需要这份文档？

答案不明确时，默认不创建。

同时满足以下条件时，才建议新增长期文档：

1. 内容描述当前系统长期有效的事实、约束、设计或决策；
2. 单纯阅读源码难以快速、可靠地得到这些信息；
3. 预计会被未来多个任务重复使用；
4. 项目愿意承担持续维护成本；
5. 仓库里没有其他权威来源已经表达相同内容。

## 3. 默认不得进入 `docs/` 的内容

除非用户明确要求长期保存，否则以下任务级内容不进入正式文档目录：

- AI 调研报告和一次性代码分析；
- 实施计划、开发计划、TODO 列表；
- Debug、排错过程和临时检查报告；
- 临时技术方案和 Brainstorm；
- AI 推理过程、Prompt 草稿、会话摘要；
- Handoff、交接记录和任务执行日志；
- 一次性代码审查记录；
- 为当前任务临时生成的上下文材料。

正式文档不使用 `xxx-v2.md`、`xxx-final.md`、`xxx-final-v2.md` 等方式堆叠版本。存在权威文档时直接维护该文档。

## 4. 临时智能体工作目录

复杂任务确实需要把计划、调研或中间状态落盘时，使用：

```text
.agents/work/
```

约束如下：

- 能不创建文件就不创建；
- `.agents/work/` 默认不进入版本控制，也不参与项目格式化检查；
- 任务结束后允许删除；
- 临时材料中出现长期价值结论时，重新整理后再晋升为正式文档；
- 不把整个临时报告直接移动到 `docs/`。

## 5. 单一事实来源

创建或扩展 Markdown 前，先检查以下来源是否已经能够表达该事实：

- `README.md`、`AGENTS.md`、现有 `docs/`；
- 配置文件；
- Zod Schema、Drizzle Schema、Migration；
- OpenAPI 或其他机器可读协议；
- 源码和测试。

能够由代码、配置或 Schema 机器化表达的信息，优先维护机器可读来源。

当前模板中的权威来源包括：

| 信息                              | 权威来源                                              |
| --------------------------------- | ----------------------------------------------------- |
| HTTP 序列化结构、错误码、输入校验 | `packages/contracts`                                  |
| 数据库表结构                      | `apps/api/src/modules/infrastructure/database/schema` |
| 数据库演进历史                    | `apps/api/drizzle`                                    |
| 国际化资源                        | `packages/i18n/src/locales`                           |
| UI Primitive 实现                 | `packages/ui`                                         |
| 可执行测试合同                    | 对应 Unit / Integration / E2E / Architecture Test     |

文档主要解释这些机器可读事实背后的长期边界、原因和协作规则，不复制大量字段清单。

## 6. README 与智能体指令

`README.md` 面向项目使用者和开发者，保持简洁，重点说明：

- 项目是什么；
- 如何安装和启动；
- 如何测试；
- 关键代码入口；
- 长期文档入口。

`AGENTS.md`、`CLAUDE.md` 等智能体指令只记录：

- 当前项目特有的硬约束；
- 无法从代码简单推断的规则；
- 必须遵守的开发和验证方式；
- 重要目录和长期文档入口。

复杂知识放入对应长期文档，智能体按任务需要读取。

## 7. 文档维护

修改代码时，如果改变了已有长期文档描述的事实，应同步更新对应文档。

发现以下情况时优先修正、合并或删除现有内容：

- 文档已经过期；
- 两份文档相互冲突；
- 文档描述和代码不一致；
- 多份文档重复描述同一事实；
- 临时任务材料被误放入正式文档目录。

不要通过继续新增 Markdown 来解决已有文档混乱。
