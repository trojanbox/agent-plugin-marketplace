# Practical Usage Guide / 实操使用指南

## 唯一目标

把复杂系统写成一份**第一次接触的人也知道下一步具体怎么做**的使用指南。

重点回答：

1. 我什么时候需要它？
2. 我可以直接怎么说 / 怎么操作？
3. 系统接下来会做什么？
4. 我需要做决定吗？
5. 完成以后下一步是什么？

本 Skill 不以“介绍全部功能”为目标。

## Skill Composition

- `writing/clear-writing` 是必需基础能力，负责最终文本清晰、具体、易扫读。
- 用户明确要求指南“去 AI 味 / humanize / 别像 ChatGPT”时，可在使用路径和事实结构已经稳定后组合 `writing/humanizer`；Humanizer 不能改掉系统真实能力、阶段边界或操作步骤。
- 本 Skill 负责**使用路径、示例组织、阶段关系和操作语境**，不要把职责退化成普通润色。

---

# 一、什么时候使用

高信号请求：

- “给我写一份这套东西平时怎么用的说明。”
- “不要介绍 Skill 干嘛，告诉别人实际怎么说。”
- “拿一些我们真实对话举例，让新人知道怎么用。”
- “写个简明操作手册。”
- “这个工作流从开始到结束，用户应该怎么配合？”
- “告诉大家什么时候讨论、什么时候出开发计划、Prompt 怎么交给 Codex。”

不使用：

- API / SDK / 协议参考文档；
- 逐字段技术规范；
- 纯功能清单；
- 一段已有文字的一般润色；
- 创建/修改 Skill Runtime 本身（`ai-workflow/skill-system-design`）。

---

# 二、先建立真实使用路径

写之前先从用户提供材料或当前系统事实中提取：

- 用户真实目标；
- 高频入口；
- 典型任务顺序；
- 哪些阶段需要用户决定；
- 哪些阶段系统会自动推进；
- 阶段交付物；
- 下一阶段怎么启动；
- 常见误用或不需要做的事情。

如果材料没有支持某一步，不凭一般知识补成“系统会自动完成”。

---

# 三、以“任务”组织，不以“功能目录”组织

优先结构：

```text
我想先把问题聊清楚
→ 直接这样说
→ 系统会做什么
→ 什么时候结束
→ 下一步怎么说
```

而不是：

```text
Skill A：功能介绍
Skill B：功能介绍
Skill C：功能介绍
```

用户通常记得“我要干什么”，不会先记住内部模块名称。

---

# 四、真实示例优先

如果当前对话、项目材料或用户提供的历史表达中已有真实用法，优先抽象这些表达。

示例要满足：

- 口语化；
- 可以直接复制改几个词使用；
- 保留真实阶段意图；
- 不为了显得完整增加系统没有的能力。

例如：

```text
你可以直接说：
“这个需求咱们先讨论一下，暂时别开发。”
```

比：

```text
调用需求讨论模块以完成需求澄清。
```

更适合作为使用指南。

---

# 五、阶段型工作流要写“怎么接下一棒”

对于 Discussion → Spec → Plan → Agent Execution 等流程，每个阶段至少写：

- **什么时候进入**；
- **你可以直接怎么说**；
- **系统主要产出什么**；
- **什么情况下不要进入**；
- **下一步怎么启动**。

尤其要写清用户需要参与的 Gate，例如：

- 需要做方案选择；
- 需要确认合同；
- 需要把生成的 Agent Prompt 交给另一个执行环境。

不要让指南停在“生成了一份开发计划”，却不告诉用户之后怎么真正使用它。

---

# 六、保持内部名词克制

内部 Skill 名称、Category、技术架构可以出现，但只在它能帮助用户理解时出现。

推荐：

> 想先讨论方案时，直接说“先讨论，不开发”。系统会进入讨论阶段并记录决定。

弱于：

> 使用 `github-discussion-facilitator` Skill。

如果读者是 Runtime 维护者，可以在正文后附一张“用户说法 ↔ 内部 Skill”对照表；普通使用者不需要先学习内部目录。

---

# 七、说明“什么情况下不用”

好的使用指南也要降低误用。

例如：

- 小修复已经非常明确，不一定需要完整讨论；
- 只是查一个接口事实，不需要先建开发计划；
- 真实运行测试要交给具备对应环境的 Agent；
- 只有需要长期记录决策时才进入对应持久化流程。

只写“都能做什么”会诱导所有任务走最重流程。

---

# 八、推荐输出结构

根据复杂度选择，常用版本：

## 1. 先记住这条主线

用一行或短流程说明最常见路径。

## 2. 平时直接这样用

按真实任务分 4–8 个小节，每节包含：

- 场景；
- 可直接说的话；
- 会发生什么；
- 下一步。

## 3. 哪些情况可以跳过阶段

只写真实规则。

## 4. 常见误区

控制在最重要的 3–5 条。

## 5. 一张速查表（适用时）

| 我现在想做什么 | 直接怎么说 | 接下来会发生什么 |
|---|---|---|

不要为了“像文档”强行加入背景、愿景、术语表、版本历史等无关章节。

---

# 九、内容密度

使用说明需要“够用”，不追求极短。

过短的典型问题：

- 只列内部模块名；
- 每项一句定义；
- 没有真实说法；
- 没有阶段衔接；
- 没有说明下一步。

过长的典型问题：

- 把实现原理全部塞进去；
- 每个内部功能写一章；
- 重复解释同一阶段；
- 加大量用户平时不会遇到的边缘流程。

目标是：**用户用的时候能快速找到自己当前这一种情况。**

---

# 十、真实性规则

- 示例只能建立在来源材料支持的能力上；
- 不把“可以讨论的未来功能”写成当前已支持；
- 不声称按钮、命令、自动跳转存在，除非材料支持；
- 当前系统需要人工把 Prompt 交给 Codex，就明确写人工动作；
- 如果不同环境能力不同，说明边界，不用模糊词掩盖。

---

# 十一、强制检查

- [ ] 文档围绕用户任务组织，不是内部功能目录；
- [ ] 每个主要场景都有“什么时候用”；
- [ ] 每个主要场景都有可直接复用的说法/操作；
- [ ] 写清系统随后会做什么；
- [ ] 阶段型流程写清下一步怎么接；
- [ ] 真实需要用户决策的 Gate 已明确；
- [ ] 写清至少最重要的“不用/不要这样用”；
- [ ] 没有发明来源未支持的功能；
- [ ] 内部术语没有压过实际使用表达；
- [ ] 经过 clear-writing 后仍保留全部关键事实和边界。
