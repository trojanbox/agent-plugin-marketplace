# 小说创作 Issue 工作流

只有用户明确要求 GitHub 持久化、已有作品 Issue 需要续接，或当前项目已经约定用 Issue 跨会话保存时读取。用户明确 chat-only 时不使用。

## 【创作】Issue

新作品创建 `【创作】<作品暂定名/主题>`；同一作品同一轮继续原 Issue，不因新场景或改名重复创建。

正文保存**当前有效共识**，只写实际已有内容，可按需包含：

- 当前故事架构；
- 核心人物与关系；
- Story Movements；
- 作品身份 / Reader Experience / POV / 时间范围；
- Story Development Plan；
- 表达合同；
- 明确不要；
- 有意保留的开放空间。

不要为了模板完整创建空章节。

评论只保存**真正改变作品的高影响决定**：

- 本轮决定；
- 理由/偏好；
- 边界；
- 影响范围；
- 被替代方向；
- 仍未决项。

低影响聊天无需每轮留痕。

新决定推翻旧决定时，保留历史评论，正文更新为当前有效版本；需要时在新评论说明 supersedes/替代关系。

## 【正文】Issue（可选）

长期、多章节写作若用户希望 GitHub 保存，可另建 `【正文】<作品名>` 并链接【创作】Issue。

建议：

- Issue 正文保存当前稿状态、章节索引、版本说明；
- 每章/自然叙事单元可用独立评论；
- 同一章小修优先更新原评论；
- 大版本重构需要保留历史时冻结旧正文 Issue，再新建下一版；
- 不覆盖用户明确要求保留的历史版本。

## 真实性与失败

- 只有真实 GitHub 写操作成功后才能声称已创建/更新。
- 远端暂时不可写时继续独立可完成的创作，并明确“尚未同步”；恢复后再补写。
- 不建立 story.json、event journal、ready_to_write/canWrite 等影子状态机。
- 跨会话没有 Issue/文档可恢复时，诚实说明缺少持久上下文，不伪造历史决定。
