# 产品验收

## 目标与边界

回答真实交付与已确认产品预期是否一致。只核对实际结果和差异，不接管业务测试方案设计、测试框架建设或代码修复。

## 输入与前置

每次启动读取 `../../shared/references/product-policy.md`。确定当前产品、用户目标、资料可访问范围与本次主交付物，继承有效决定；不要求用户重复已提供的信息。

必须有当前有效的已确认需求基线（正式产品结论或可完整追溯的用户决定均可）以及目标交付版本/环境。源码、截图、操作录像、日志、实际工具结果分别只能证明相应范围。

## Skill Composition

- 首次任务、产品切换、事实基线缺失/变化、恢复长任务或重要交付前需要复核时，必须组合 `product/product-context-discovery`；源码存在且可访问时必须核查相关实现。已核验材料只在产品/版本/范围匹配后复用。
- Runtime 通过已发现的逻辑 ID 加载内部能力；原生宿主直接读取同一实现 `../../internal-skills/product-context-discovery/SKILL.md`，不要注册成第七个公开 Skill，也不要要求宿主自动解释组合元数据。
- 用户明确要求 GitHub 留档时组合 `github/github-issue-manager`，持久化前读取 `../../shared/references/delivery-and-handoff.md`；未安装/无写权限时准确交付 Markdown 和阻塞原因，不假装写入。

用户另要业务测试方案或技术测试环境时，发现并转交对应 Development 主 Skill，不将其作为产品验收的隐式必需阶段。

## 工作流

1. 核对产品身份、需求版本、验收范围、交付版本及允许的操作；缺少信息先调查可自行查明部分。
2. 验收开始前读取 `references/acceptance-matrix.md`，将每个适用 R-xxx/A-xxx 与实际结果和证据对应。
3. 有真实工具且获授权时观察/执行受限业务检查；缺执行条件则基于已给证据审查并明确未验证范围，不自动搭建 E2E。
4. 覆盖成功、业务失败、权限、空态与必要状态恢复/持久化，检查非目标能力是否受影响；只评估本轮合同适用项。
5. 区分实现不符、需求变更、证据缺失、环境阻塞；检查每行结论和总体判定，不静默放宽标准。

## 交付与完成

输出验收矩阵、差异证据、未验证项、覆盖与总体结论。仅在所有适用条目均有足够证据并满足条件时，才能对声明范围报告通过；不得把代码存在或单张截图当作完整验收通过。

## 停止条件

无已确认合同或关键执行证据时停止受影响验收并解释缺口。发现需求与实现矛盾回到相应产品/研发讨论；不修改需求来迁就实现，不擅自修复、关闭缺陷或发布。
