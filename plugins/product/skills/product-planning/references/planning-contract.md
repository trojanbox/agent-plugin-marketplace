# 产品规划合同

制定定位/MVP 时读取；规划可含备选和假设，不能把建议升格为用户决定。

## 从用户任务到最小闭环

1. 问题：谁在什么场景下遇到什么阻碍，现有替代方式有哪些，证据能证明多大范围。
2. 定位：目标用户与非目标用户、核心价值、使用频率/触发条件和明确业务限制。
3. 场景：入口 → 用户动作 → 获得结果 → 失败/退出；新产品也要定义用户如何完成任务。
4. MVP：保留完成核心任务必需的能力和约束，明确首版不做项及依赖。未实现能力标明待建设；用户未要求的新平台依赖只指出，不发散设计。
5. 验证：哪些观察能支持/否定价值假设，何时应调整范围。指标可提出候选定义/观察方式，但无基线就不编造数值、阈值、转化率或商业收益。

已有产品重新规划先列需保留的现有行为、已有用户任务、迁移影响与不可破坏条件；不凭“新架构更合理”替用户废弃现有能力。

## 建议的 Markdown 结构

- 一段说明产品、用户问题和本次规划目标。
- 事实基线与来源，区分已知/假设/待验证。
- 定位与关键用户场景。
- 核心流程图（有多步骤时）及失败边界。
- 首版能力、优先级依据、依赖、非目标与延期。
- 可复用能力/真实约束、关键风险与验证方法。
- 待用户决定的问题与有依据的推荐。

优先级理由结合用户价值、问题频度的实际证据、约束、风险与依赖；无可靠数量时使用定性描述，不捏造评分。明确硬约束与可以调整的习惯，不能把当前技术限制直接当永久产品规则。

## 完成检查

每项首版能力可回到用户任务及证据；假设有验证方式；非目标真实约束范围；重要取舍未确认就留在讨论。交付计划不等于产品需求冻结，不自动创建工程实施计划。
