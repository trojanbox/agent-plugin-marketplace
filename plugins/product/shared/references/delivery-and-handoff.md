# 交付、持久化与研发交接

准备生成正式记录、写入项目管理工具或交接研发时读取。

## 持久化

默认产物为可独立阅读的 Markdown。用户要求正式讨论留档时先检查现有同轮记录；按当前产品配置选择载体。GitHub 只是一个适配器，不是必需环境。每次写入确认目标仓库、目标记录、内容和授权；不能沿用另一产品的目标仓库。

GitHub 写入先发现并加载 `github/github-issue-manager`；引用其实际安装目录中的恢复/交接协议，不猜兄弟插件路径。缺失 GitHub 能力时保留当前 Markdown 并明确尚未写入；有明确本地交付授权才保存本地文件。其它载体同样核对真实工具和权限，不声称自动支持任何未连接平台。

正式讨论复用同轮；执行类 Issue 的查重由 GitHub Manager/Triage 承担。新建/更新前重读远端，检测并发变化；无法安全合并时停止该写入。写后重新读取并核对内容、仓库、编号和状态。读取权限不包含关闭、删除、指派或发布权限。失败不得吞掉，也不重复盲目创建。

无项目命名约定时可采用【产品·调研】【产品·讨论】【产品·结论】【产品·体验审查】【产品·验收】；规划可采用【产品·规划】。既有项目规定优先，标题不决定主路由。纯粹代发用户已完成正文归 GitHub Manager。

## 产品与研发交接

产品结论明确目标用户、场景、需求 R-xxx、业务边界、失败表现和验收 A-xxx；用当前事实说明可复用能力和真实限制。开发 Skill 接收这些已确认决定并决定工程实现，不重新选择已确认产品行为；高影响的新技术限制须回到相应决策层，不静默改需求。

进入 `development` 前按当前任务目标发现适合的讨论、开发结论、实施计划或测试方案 Skill，并执行其 Gate。产品结论不能自动冒充 `development` 要求的开发结论，产品验收也不替代单元/集成/技术测试。

用户明确说“无需单独结论，直接基于已确认讨论开发”时记录 `spec_skipped_by_user`、来源、理由、风险和实际授权范围，继续交接研发阶段处理；不暗中补建结论，也不将未决关键事项视作已确认。只有“暂时不创建结论”且未要求开发时仍停留讨论。

## 交付前检查

- 完整读取当前有效决定，未知不伪装成已确定目标；事实来源匹配产品和版本。
- 需求、流程、异常路径、边界和验收能双向对应；非目标不被下游扩大。
- 业务内容在当前产物内完整，来源链接仅帮助验证，不代替规则说明。
- 明确本次仅调查/生成文档/核对结果，还是实际执行了什么操作。
- 分别报告写入成功、失败、未执行；未运行验证保留为未验证。
