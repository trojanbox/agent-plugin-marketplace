# 所有新产品：广度优先的全局骨架合同

## 触发范围与阶段

- 触发：构思任何新产品（包括简单单功能产品），或对整个产品重新规划；用户明确要求“先搭骨架 / 先看全局 / 暂缓细节”亦触发。
- 非触发：已有产品的局部问题、已确认骨架后的单模块细化；不机械扩大用户没有要求的模块。简单产品同样先做极简整体骨架。
- `skeleton_draft`：根据用户资料列出**候选**模块和关系、已知/未知；不把推荐视为决定。
- `skeleton_review`：逐一检查模块覆盖、与外部系统的交互边、核心路径及交叉影响；收集用户对全局的调整。
- `skeleton_confirmed`：用户明确认可**整体范围和模块边界**，只冻结这个高层骨架版本；可以继续讨论模块内部规则。整体骨架确认不等于产品结论/技术架构确认。

## 一次交付的最小骨架（对未知如实标记）

1. **目标与边界**：目标用户、核心任务、已确认非目标、此次讨论范围。复用已有决定；不要添加猜测的行业能力。
2. **完整功能与模块清单（能力级）**：每个模块的单句职责、提供给谁、属于平台核心/插件或扩展/外部系统/部署环境，标注 `已确认 / 候选 / 未决`；列出暂缺但影响闭环的能力，不展开实现。简单单功能产品只用几句话盘点全貌。
3. **交互关系**：画出用户入口 → 关键平台能力 → 插件或扩展 → 外部服务 → 结果与错误反馈的典型路径，并分别指出跨模块输入/输出和责任归属。只确认协作语义，不冻结具体 API 或存储模型。
4. **跨场景覆盖**：已有企业 vs 新企业、本地 vs 云端、短任务 vs 长任务（只检查当前用户已提出的适用维度），避免单一模块决定暗中改变其它路径。
5. **横向约束**：身份/授权、执行与任务状态、失败与退出、数据归属、模型/成本的**涉及模块与未知边界**。每项先标明覆盖范围，不进入独立详细方案；无需按清单强加用户未要求的新基础设施。
6. **依赖和冲突清单**：哪些模块必须互相认识/提供能力、外部系统缺什么条件、某方案会改变哪些其它模块。列出少量影响全局的 Q-xxx，具体模块细节先列“后续细化”，不要逐个全部问完。
7. **整体骨架审查**：邀请用户一次审阅遗漏、错误归属和外部连接；用户没有明确整体确认时只交 `skeleton_draft / skeleton_review`，不能将单模块选择提升为骨架已定。

## 广度优先的推进门槛

规模仅影响表达深度，先广度后深度的顺序对任何新产品都适用。

- 同一轮先覆盖所有已知模块与外部连接，检查用户触达路径是否有断点，才选模块纵向深入。
- 用户主动提出单模块细节时，可以解释其对全局的影响、记录待细化决定；若会改动其他模块边界，先更新骨架并重新进行整体审查。禁止“先把这个模块全部定完”造成局部锁定。
- 用户明确了局部方案时，保留 D-xxx 的真实选择与适用边界；骨架变化只能把其它受影响项标为待复核，不能静默篡改历史。
- 在产品骨架层只讨论**模块职责、交互能力、产品体验与约束**；技术接口、分布式算法、数据库、框架实现留给后续研发调查/技术阶段，且需明确授权。
- 已确认骨架后可以逐模块讨论；新增跨模块能力需说明对骨架的变更，再决定是否回到全局审查。

## 交付检查

必须能回答：模块是否覆盖用户已给的全部方向？哪些由外部/插件负责？每条跨边界调用由谁发起、谁回结果、失败谁可见？本地/云端等已确认形态是否矛盾？未决事项是否集中在高影响边界？**是否获得用户对整体骨架的明确认可？** 未获得整体确认则继续广度讨论，不进入细部收口。
