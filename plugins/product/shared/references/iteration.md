# 使用反馈与回归维护

仅在用户要求改进 Product Skill、记录已发现使用问题或维护发布时读取；普通产品任务不自动开始维护或后台监控。

## 保留最小反馈

记录原始请求的必要脱敏片段、产品类型、输入/源码版本、主 Skill 与 Plugin 版本、实际产物、预期差异、来源、复现步骤、影响范围及失败样例。先确认信息能否留档，不拷贝凭据或不相关私有数据。尽可能把案例归纳为通用的最小重现材料，同时保留验证依据。

区分路由漏选/误选、主目标冲突、证据不足、阶段越权、产物遗漏、交接不一致、单纯风格偏好；同根因合并，不为数量制造问题。真实使用反馈优先，构造样例必须标注 synthetic，不能当作真实客户研究。

## 修订循环

1. 确认本次维护授权和影响的现行合同，保留原始失败样例。
2. 先写预期和回归条件，再修相关主文件/引用/组合规则；避免顺带重写稳定邻居。
3. 验证新增样例、相关历史样例、负例、双主目标、组合和多轮授权 Gate。
4. 更新宿主 manifest，运行结构/引用/合同检查和 doctor；模型逐条语义审查与自动化结果分开记录。
5. 做产品产物的来源覆盖检查；验收样例必须包含缺证据和失败分支。
6. 检查 Diff、未提交他人改动、版本与变更说明；仅在用户授权内提交或推送。

没有多次独立评估不能报告总体准确率。未经授权不自动修改 Skill、收集其它项目资料、提交或发布。失败时保留原因及复现证据，不放宽门槛伪造通过；修订完成后由新的案例继续完善，首版不新增重型 E2E 平台。
