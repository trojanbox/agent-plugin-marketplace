# 产品事实与上下文调查合同

内部调查首次建立基线、来源变化或复核时读取。共享的是调查规范，各产品事实必须项目隔离；首版不建立跨产品知识库、自动同步或持久化数据库。

## 1. 确定范围与调查深度

| 场景 | 最小充分调查 | 何时扩展 |
| --- | --- | --- |
| 局部体验改进 | 受影响入口、用户任务、相关组件/接口/权限与直接反馈 | 发现共享状态、多个入口或跨功能副作用 |
| 已有产品跨功能需求 | 从入口到结果的关联业务链、对象关系、状态/失败分支及用户证据 | 依赖跨模块/外部服务，或源码与文档冲突 |
| 新产品/重大规划 | 用户目标、现有替代办法、业务约束、必要市场/竞品证据；有原型或源码也查 | 关键定位/可行性取舍缺证据 |

深度由影响面解释，不设置任意文件数、页数或调查时长阈值；不要每次全仓扫描。来源足以支持当前决策且关键未知已显式界定时结束调查；高影响未知阻塞受影响决定。

## 2. 建立最小事实卡

至少包含下列信息；这是 Markdown 数据合同，不要求新建数据库或 JSON 文件：

- `product_id` / 项目或仓库：当前唯一目标，来自用户或可靠项目配置。
- `mode`：新产品 / 已有产品；本次问题、范围、非目标。
- `baseline`：Git 仓库、分支、完整 HEAD、dirty 状态及受影响文件；附件名称和可取得的内容摘要/哈希；文档版本；运行环境/build。
- `as_of`：核对时间与资料发布日期/实际事件时间；不要只用抓取日期冒充内容新鲜。
- 有效决定、现有能力、实际限制、关键未知、资料可访问性、允许的操作。

产品未明确但当前上下文可唯一确定时直接读取验证；确有多个候选且会污染事实时停止跨产品推断，只提出必要澄清。

## 3. 有相关源码必须核查

先读根目录及适用子目录的 AGENTS.md、项目约定和相关 Skill。沿本次用户动作追踪入口 → 业务规则 → 接口/状态/数据 → 输出/失败路径 → 相关测试。检查定义和消费是否实际接通，不能用“存在文件”证明功能已可用。

以当前源码/测试/配置证明实现，运行日志证明观测行为，文档和历史 Issue 补背景。源码存在但无法访问时明确“源码未读取”，写明对结论的限制；不能把“访问失败”误写为“项目没有源码”。新产品本来没有源码时允许继续基于现有业务资料工作。不得用公共搜索到的同名仓库替代用户项目。

不读取 .env 原值或凭据。跨模块完整技术调研必要时仅复用 Development 的只读调查方法并带回证据；本次产品主交付物不改变，副作用不随辅助 Skill 扩散。

## 4. 证据账本

| ID | 类型/产品 | 来源与 locator | 版本 / as_of | 实际支持的主张 | 状态/限制 |
| --- | --- | --- | --- | --- | --- |
| E-xxx | 源码/反馈/文档/日志/外部资料/用户决定 | 路径+符号/章节/真实 URL；行号只作快照辅助 | HEAD、构建号或日期 | 仅写该来源能证明的内容 | verified / partial / pending / stale |

每个关键事实有来源；假设和推断另标，不把“用户说存在”直接升级为实现已核验。统计证据记录样本口径、时间窗口和缺失数据；无数据就保持未知。明确未验证的观察边界，例如截图只覆盖一个状态。

## 5. 冲突、复用与刷新

材料冲突时先核对产品、分支、环境、版本、时间与概念口径，区分当前行为和期望规则；无法解释的冲突保留并指出影响。代码更改不自动推翻用户决定，决定更新也不证明代码已更新。

复用前比对同一产品与本次范围，检查相关源码和材料是否变化；HEAD 相同也要核对 dirty 文件、外部配置/运行环境。有变化只重查受影响证据及传播链；未变化可复用已核验结果，不能跨产品继承事实。切换阶段/恢复任务/关键写入前重新读取权威材料和限制。

## 6. 返回给主 Skill

返回事实卡、必要来源索引、当前能力/限制、已确认决定、未知/冲突、调查覆盖与未覆盖范围、受影响的决策。状态为 `sufficient`、`partial` 或 `blocked`，附理由。`partial` 允许主 Skill 处理不受未知影响的内容，不允许冻结依赖未知的高影响规则；绝不自动创建报告、Issue 或新结论。
