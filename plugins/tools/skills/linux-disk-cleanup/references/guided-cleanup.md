# Linux 用户磁盘清理：对话引导与最终确认

适用于「帮我清磁盘」「服务器空间满了」「找一下占空间的大目录」「清旧缓存」等。**优先定位占用，再考虑删除**；缺少清理对象、目标主机或具体授权时，只读检查。

## 1. 只读检查磁盘现状

- 确认当前实际访问的 Linux 主机属于用户授权范围，以普通 UID 操作，不调用 `sudo`、`rm` 或其它破坏性工具。
- 先使用工具 `doctor` 检查当前普通用户与可用清理范围，再 `report` 获取真实文件系统容量和 home 目录前 25 个空间热点。`report.truncated=true` 时所有目录大小只是已扫描范围的**下限**；home 可能和系统目录在同一文件系统，也可能位于不同挂载点。
- 如用户只想了解问题，给出占用的直接证据并结束。不要把只读扫描等价为获得了删除授权。
- 如果占用来自 Docker 数据、系统日志、数据库、项目 node_modules、下载文件、回收站、系统临时目录等，**明确说明当前 Skill 没有对应自动清理能力**，可以解释原因，但不能顺势创造删除流程或运行 `docker prune`、`journalctl --vacuum`、`rm -rf`。

## 2. 只问缺失的配置

- 仅支持三个固定目标：`user-cache`（`~/.cache`，旧普通文件）、`npm-logs`（`~/.npm/_logs`，旧日志）与 `npm-cache`（`~/.npm/_cacache`，**使用 npm 官方 `npm cache verify`，不按文件年龄删除**）。先展示 `report` 发现的真实占用，再说明各项清理风险与实现差异。
- 用户说「清理 npm 缓存」则只读 `scan --scope npm-cache`，清楚说明 npm 使用内容寻址缓存，原生 `verify` 会核验并回收不再需要的数据，但**不能只处理 30/90 天以前的文件，也不能事先列出将被回收的具体块或准确空间**。若用户坚持按年龄清理 npm 缓存，当前功能无法满足，停止操作。
- 若用户只说「帮我清理磁盘」，先诊断，说明可清理的固定类别；**一个关键问题一次问**，例如「先检查用户缓存还是 npm 缓存？」；不要请求用户自己拼脚本/命令，也不要对全家目录执行递归删除。
- **仅** `user-cache` 与 `npm-logs` 使用 `--older-than 30` 默认值，用户可指定 1–3650 天；`npm-cache` **不接受 `--older-than`**。
- 不询问或读取凭据/文件内容；只收集允许范围内的相对路径、大小、修改时间等元数据。

## 3. 展示计划并取得确认

先执行只读 `scan --scope <scope> --older-than <days>`（npm-cache 只执行 `scan --scope npm-cache`），向用户展示：

- 普通缓存：实际根目录、固定类别、年龄阈值、候选数量、预计逻辑大小及最大 15 项。npm-cache：真实目标、当前扫描文件数量与总逻辑大小、将运行 `npm cache verify`；**拟回收多少文件/空间均未知**。
- `scan` 给出的精确 `plan` 指纹，它与当前候选文件清单及元数据绑定；任何新旧文件变化、scope 或年龄变化都需要重新 `scan`；
- 提醒不会删除目录、软链接、硬链接、其他用户文件、项目源码、数据库与系统日志；文件删除后**无法撤销**，部分运行中的软件可能需要重新生成或下载缓存；白名单目录内若混放了业务文件，过滤规则未必能识别，用户必须检查是否有重要文件；
- 提醒逻辑字节数不是实际回收空间的保证，若 `report.truncated` 或超限，需明确标记数据不完整。

随后询问用户是否接受当前具体清理方案；聊天中的「确认」**只表示意愿，不会直接授权 CLI 删除**。用户需自行在**目标 Linux 本机交互终端**输入计划绑定的 `DELETE <scope> <SHA前12位>` 挑战短语；CLI **不再接受 `--confirm yes`**，无本地 TTY 一律拒绝执行。更改范围/天数后必须重新 `scan`；Agent 严禁代输入、伪造伪终端或绕过 CLI。由于 Agent 若已获得同一 UID 全量 shell 权限，仍能模拟终端/直接执行文件删除，这只能防无人值守操作，不能保证密码学意义的真实人工身份认证。要实现不可伪造审批，需要宿主独立可信授权通道。

## 4. 授权后执行和复核

- Agent 提供用户可在目标主机终端手动运行的命令：`clean --scope <scope> --older-than <days> --plan <SHA256>`；npm-cache 省略天数。**Agent 不代运行交互式删除、不可复制自造答复给进程**。用户需看终端展示的目标、范围、数量/机制，并手输该次计划的挑战语句。若无交互终端，返回 `approval_required`，停止。
- CLI 校验计划、可检查的候选身份，要求终端确认后**再次全量扫描**；普通缓存逐个复核后删除。`npm-cache` 严禁直接删除 `_cacache` 中的任何条目，只使用 npm 官方 `npm cache verify --cache <当前用户家目录>/.npm --offline --ignore-scripts` 完成原生完整性检查/垃圾回收。
- 成功后重新 `scan` 或 `report` 读取真实状态：普通缓存报告 `deleted_count`、`estimated_bytes`，npm 的 `maintenance_completed` 仅说明原生维护执行结束，不保证精确释放字节。普通缓存 `partial_change` 表示中途已部分删除，npm `maintenance_failed` 表示原生命令失败且内部状态可能改变；均须停下核实，**不声称实测释放了 estimated_bytes**。文件内容不会打印。
- 失败时区分「未删除」「已删除部分文件」「目标已变化需重新预览」，禁止吞错、无依据重试、以 sudo 兜底或换成系统清理命令继续。

## 对话示例

### A：仅诊断

用户：「服务器磁盘快满了，看看什么占空间。」
Agent：`doctor` + `report` 只读，告知文件系统容量、家目录热点和是否截断；用户没授权，任何缓存都不删除。

### B：已有明确目标

用户：「把旧的 npm 缓存清理一下，保留最近一个月的。」
Agent：`scan --scope npm-cache`，明确「无法仅保留最近一个月的 npm 缓存」，给出改用 npm 原生 `verify` 的选项。用户同意后还需亲自在本地终端完成挑战确认；不运行按年龄删除。

### C：变化与失效

用户：「我确认了刚才那份旧缓存清理计划。」
Agent：只向用户提供与原计划完全一致的手动命令；用户在终端确认过程中若缓存发生变化，CLI 返回 `stale_plan`，需重新扫、重新展示与重新授权，**不能强行清理或自动重试**。

### D：超出范围

用户：「把整个 /var/log、Docker 卷、项目 node_modules 都清掉。」
Agent：当前仅支持用户缓存和 npm 日志，明确告诉用户这些范围**当前没有自动清理功能**，保留诊断信息，不执行 shell 删除，不擅自给系统权限。
