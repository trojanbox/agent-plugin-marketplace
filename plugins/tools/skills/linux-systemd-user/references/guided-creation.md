# 创建 systemd 用户服务：对话引导合同

本流程只在用户要求**新建 service**、把程序常驻后台或设置用户级 systemd 自启时激活。Agent 负责提问、只读核对、预览与执行；**原 CLI** `shared/scripts/systemd-user.mjs` 保留为底层操作入口，不要求用户手动拼接 CLI 参数，也不新增终端交互式 wizard。

原则：自然语言对话、**一次只问一个关键问题**，用户一次提供了多个字段就一并接收。优先使用用户这轮/前几轮已经确认的事实；不重复询问，不按固定表单把所有字段重新填一遍。能从已授权的当前项目文件**只读核实**的值可预填，并标明来源；不确定或冲突的字段先问清，绝不静默猜测。

## 1. 只读预检

1. 确认目标是当前 Linux **普通用户**的 `systemctl --user`，操作目标机器必须是用户授权的机器。系统级/root service、跨用户操作不在本 Skill 范围。
2. 使用当前安装 Plugin 的真实 CLI 路径运行 `doctor`；检查 `user_manager_available` 和 `linger`。若用户管理器不可用，说明真实阻塞并暂停创建；用户仅要求方案草稿时可继续给出不执行的预览。不要为了「修好」自行调用 sudo 或修改系统权限。
3. 若上下文已给出项目目录/启动脚本，可对已授权项目进行**只读**检查：启动入口、package scripts、解释器实际绝对路径、启动参数、目录、已有 unit 名称冲突。只读检查不运行目标程序、不写文件、不启用服务；只有能核实的命令才可作为已知参数。比如 `command -v node` 可定位解释器，但不可把某台机器上的 `/usr/bin/node` 猜给另一台机器。
4. 未知目标程序的情况下，应优先问程序或现有启动命令；不要先问十几个 systemd 细节。遇到 `already_exists`/现有同名 unit，**禁止静默覆盖**、改用 `update` 或自动取新名字；先明确告诉用户冲突，选择其他名称需要重新确认。

## 2. 补齐缺项

提问顺序只作为**缺项优先级**，跳过已知项，正常每轮一个关键问题；用户回答多个字段时直接合并进当前草案：

| 配置 | 获取方式 | 没有明确要求时 |
| --- | --- | --- |
| 启动命令 | 用户给出原有命令，或从授权项目只读核实可执行文件、完整 argv；将可执行程序解析成真实绝对路径 | **必需**。缺失就问「这个程序平时怎么启动？可以发命令或程序目录」 |
| 服务名 | 从已知应用/目录建议合法 ASCII 名称并检查冲突；若名称不明确或冲突则问 | 建议一个名字，交给用户在最终预览确认 |
| 工作目录 | 根据已核实应用目录或启动方式推导；遇到相对路径需求、多个候选或不确定则问 | 可省略，不能随意猜当前 `cwd` |
| 参数和环境文件 | 仅采用明确的 argv 和必要的 `--env-file` 路径；环境文件须为当前用户所有且权限不超过 0600 | 参数默认空；无环境文件默认不配置；不读取或询问明文密码 |
| 描述与失败重启 | 非关键字段，不增加没必要的来回问答 | 描述默认服务名；`Restart=on-failure` |
| 创建后是否立即启动 | 沿用用户已表达的「现在运行」「先只创建」 | 未明确授权则不启动 |
| 自动启动层级 | 用户明确「仅手动」「用户登录后自启」「无人登录也启动」时直接采纳 | 未提自启则不启用；含糊说「开机自启」时，只问一次登录后还是无人登录 |

**自启选择必须准确区分**：

- 只创建：仅 `create`。
- 现在运行：`create` 后 `start`；不隐式 `enable`。
- 用户登录后启动：`create` 后 `enable`；若同时明确「现在启动」，用 `enable --now`。**如果机器已启用 `linger=yes`，用户管理器可能在无人登录时已启动，此时 `enable` 也会在开机时拉起服务**。用户明确要求「只能登录后启动」时，须说明现有 CLI 无法保证该限制并停在确认阶段；不要为此擅自关闭 linger 或改动其他服务。
- **服务器重启后无人登录也启动**：除 `enable` 外还要验证 `linger=yes`。若当前 `linger=no/unknown`，必须单独说明启用 linger **影响同一用户的其他服务**的持续运行与开机行为，放入最终预览并征得明确同意；未经同意绝不调用 `linger enable --confirm yes`。用户指定只登录后启动时不要触发 linger 改动。

**命令边界**：当前 CLI 采用 **可执行文件 + 独立 argv**。用户提供 `pnpm start` 等命令时，先只读解析程序实际路径和参数；带管道、重定向、`&&`、`export` 等 shell 特性的命令不能未经确认变成 `bash -c`。需要外部包装脚本时应明确告知原因并问用户使用哪个脚本；不要自建脚本或擅自运行构建/安装步骤。

## 3. 配置预览与最终确认

所有必要字段收齐并完成只读核查后，用简短自然语言展示**将实际执行的配置**，至少包含：

- 当前用户、目标 `~/.config/systemd/user/<服务名>.service`、启动命令（`--exec` 绝对路径与全部参数）、工作目录；
- 描述/重启策略（默认 `Restart=on-failure`）、环境文件路径（如有，不泄露内容）；
- 创建后是否立即启动、是否 `enable`、属于「用户登录后启动」还是「无人登录也启动」、`linger` 现状及是否需要改变；需要 linger 时明确提示对其他用户级服务的影响；
- 可能无法完成无人登录自启的限制（例如需要 Polkit/管理员授权，或重启未实测）。

再以一句话问「**确认按上述配置创建并执行列出的启动/自启操作吗？**」；未确认前不执行写操作，包括 `create`、`start`、`enable`、`linger enable`。如果用户回复是在**修改配置**、补充命令、变更启动方式，必须重新预览确认，不能把原确认当成对新方案的授权。用户否决则停止，不创建任何 unit。

## 4. 按确认范围执行

只对已确认的当前普通用户运行原 CLI，Agent 自行构造参数数组，用户无需复制命令：

1. `create NAME --exec ABS [--arg VALUE ...] [--cwd ABS] [--env-file ABS] [--description TEXT] [--restart ...]`。仅当结果为 `created` 才进入后续操作；`already_exists` 停止并征求选择，不偷偷转 `update`。
2. 如已确认「立即启动」：执行 `start NAME`；如已确认自启：执行 `enable NAME`，已授权立即启动时可用 `enable NAME --now`。只有明确要求无人登录启动、且 `linger` 不是已验证 `yes`，并已获悉对其他用户服务的影响且明确同意，才尝试 `linger enable --confirm yes`；**不调用 sudo**。用户没有选择的动作一律不执行。
3. 若出现 `permission_required`、`partial_change`、无法访问用户管理器或其他失败，停止后续有依赖的操作，报告已完成与未完成的真实状态；不自动回滚/重试/改以 root 执行。要继续修复必须以新证据和用户授权为准。

## 5. 验证与结果报告

- 创建后检查 `status NAME`（特别是 `LoadState` 与 `FragmentPath`）；有启动/自启动作时再核对 `ActiveState`、`UnitFileState` 和需要的 `linger status`，不能只看 CLI `ok=true`。
- 只汇报观察到的事实：文件创建、加载成功、当前运行状态、启用状态、linger 配置是否已验证。**不把 enable 成功等同于开机自启已验证**，未经真实重启后检查不能宣称「断电重启后一定会运行」。
- 失败时清楚区分「未创建」「已创建但未启动」「已启用但 linger 未满足」等部分状态；**不自动回滚**刚才已成功执行的独立步骤，避免破坏其他服务。
- 如果宿主没有操作对应机器的工具/权限，只给出明确配置和未执行状态；不要假装运行过 systemd。

## 对话示例（给 Agent 判断缺项，不需要照搬话术）

### 示例 A：缺少启动命令

用户：「帮我加个 systemd 后台服务。」
Agent：「可以按当前普通用户管理。这个程序平时怎么启动？发一条启动命令或项目路径就行。」
用户：「在 `/home/alex/apps/notify`，跑 `node index.js`。」
Agent：只读检查实际 node 路径、工作目录和入口文件；从项目名提出服务名 `notify`，仅继续询问未确定的自启/立即运行需求，不让用户重复给出命令。

### 示例 B：已给出完整信息

用户：「把 `/usr/bin/node /home/alex/apps/notify/index.js` 作为 `notify` 用户服务，工作目录 `/home/alex/apps/notify`，只创建，先别启动也别自启。」
Agent：检查当前机器环境和路径，再直接展示完整预览（`Restart=on-failure`、无环境文件、只 `create`），问最后一次确认；**不逐一询问已经给出的字段**。确认后才创建，不额外执行 `start/enable`。

### 示例 C：无登录自启

用户：「重启后哪怕我没有登录，也要运行这个用户服务。」
Agent：先核对 `linger`；如为 `no`，预览必须写明将启用 linger、它**影响同一用户的其他服务**，还将配置 `enable`（如用户同时要求立即启动才 `--now`），用户明确确认后才执行。被拒授权时说明需要管理员/Polkit 并报告已创建 service 的实际状态；不请求 sudo。

### 示例 D：环境不可用

用户：「帮我创建 `demo` 的用户服务。」
Agent：只读 `doctor` 得到 `user_manager_available=false`，直接解释当前机器没有可用的 systemd 用户管理器、无法实际创建，不继续索要全套参数；如用户只想先商量配置，则继续对话但明确为未执行草案。
