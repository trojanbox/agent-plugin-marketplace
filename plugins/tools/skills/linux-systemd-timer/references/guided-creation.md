# systemd Timer 对话式创建

适用用户说「每天凌晨 3 点跑这个脚本」「定期备份这个目录」「每周一检查一次程序」等**在目标 Linux 用户账户内定时执行程序**的场景。GitHub Issue 待办与提醒仍用 GitHub 工作流；如果用户只是要提醒而没有 Linux 脚本，应避免误用 Timer。

## 阶段 1：只读确认目标环境

- 先确认目标 Linux 机器已获操作授权、执行身份为**当前普通用户**；运行实际安装的 Timer CLI `doctor`（仅只读），确认 `user_manager_available=true` 和 `calendar_parser_available=true`。缺少系统 systemd、DBus 或 parser 时停止真实创建；可展示未执行草案，不能虚构已安装服务。
- 若当前上下文已有项目目录、可执行脚本或运行命令，只读读取允许访问的项目文件及解释器真实路径（如 `command -v python3`），不执行用户脚本、不安装程序、不建包装器。
- 读取目标主机本地时区（如 `date +%Z%z`，只读），若用户提了北京时间/东京时间等时区，明确写出时区并由本机 `systemd-analyze calendar` 验证；不可偷偷把用户表达转换成另一个时区。
- 同名 `.service` / `.timer` 可能属于已有用户程序，应只读检查与提示；发生冲突不自动覆盖、改名或升级。

## 阶段 2：只问缺少的必要信息

一次只问**一个关键问题**；用户一次给出多个字段时全部接受，不重复询问已确认内容。按以下顺序补缺：

| 维度 | 必须核实的内容 | 可以采用的默认值 |
| --- | --- | --- |
| 执行对象 | 运行什么程序、完整启动命令，真正可执行文件的绝对路径与 argv；是否需要工作目录 | **无默认脚本**；缺失就问「这个任务平常怎么手动运行？」 |
| 执行时间 | 每天几点、每周几/几点、每几分钟或原生日历表达式，以及目标机器的时区 | **无默认时间**；含糊就问「具体什么时候运行？」 |
| 任务名 | 合法的 ASCII unit 名，与其他 service/timer 无冲突 | 可从项目名称建议，最终预览确认 |
| 环境文件 | 可选现有私有配置路径 | 默认为无；**不读取或询问明文密码** |
| 计划精度 | systemd 精度窗口 | `AccuracySec=1min`，若用户需要更精确可选 `1s`（仍受调度限制） |
| 漏执行后补跑 | 用户未登录、机器关机、timer 没运行时错过日历事件，恢复后是否立即补跑 | `Persistent=no`，**不自动补跑**；选择 yes 必须说明恢复时可能立即运行 |
| 创建后动作 | 仅创建、立即激活 timer、启用开机自启、是否需要无人登录运行 | 默认仅创建，不 start/enable；明确说明 timer start 是启动调度器 |
| 描述 | 便于识别的任务名称 | 默认任务名 |

把用户的「每天凌晨 3 点」转成例如 `*-*-* 03:00:00`；「周一到周五早上 9 点」可转 `Mon..Fri *-*-* 09:00:00`；「每小时」可用 `hourly`。这些都是**示例**，最终使用目标主机 `calendar EXPR` 实际校验和返回的下几次触发时间。不要把 5 段 cron 表达式直接填入 `OnCalendar`；无法准确解释的频率必须继续澄清。

## 阶段 3：预览与确认（无写操作）

- 对形成的 `OnCalendar` 先调用 `calendar EXPR`（只读），显示系统解析器返回的原始规范化结果及下 3 次触发时间。检查目标主机时区；自然语言时间和预览时间不一致则停止创建并更正。
- 向用户展示完整草案：`NAME.timer` + `NAME.service`、`Type=oneshot`、可执行文件/参数/工作目录、`OnCalendar` 和实际下次执行时刻、时区、`Persistent`、`AccuracySec`、环境文件路径（不展开内容），以及「创建后是否启用/立即激活」。
- 特别说明 `Persistent=yes` 在 timer **重新启用或用户管理器恢复时可能立即补执行一次**；这项确认与「是否开机自启」分开。`AccuracySec=1min` 表示时间窗口，不保证固定到某一秒。
- 无登录时定时运行需要 `linger=yes`；如当前为 no 或 unknown，先说明开启 linger 会影响**当前用户其他 service/timer**，只有再次获明确授权才通过既有 `systemd-user.mjs linger enable --confirm yes` 尝试授权。当前只要求登录后执行时绝不自动调整 linger。若已经是 `linger=yes`，无法保证「仅在登录后运行」，需先说明限制并停在确认阶段。
- 在最终预览后问「确认按以上配置创建吗？是否另外启用或立即激活？」；用户未明确确认前**不得执行任何写操作**，包括创建 unit、daemon-reload、enable、start、linger。用户更改时间/脚本/补跑策略后必须重新预览并取得新的确认。拒绝或取消则不执行。

## 阶段 4：执行已确认动作并验证

1. Agent 自行构造原 CLI 的 `create NAME --exec ABS --calendar EXPR ...` 参数，**不要求用户手动拼 CLI**；只有返回 `created` 且配对 unit 已加载才继续。
2. 如明确需要激活定时器则 `start NAME`；需随用户管理器启动则 `enable NAME`；明确还要立即开始调度可 `enable NAME --now`。这些操作不会主动使用 `run-now`；但 `Persistent=yes` 的 Timer 在启动或重新激活时**可能立即补执行一次**，需要用户事前知情确认。用户明确要主动运行一次时，需额外确认并调用 `run-now NAME --confirm yes`。
3. 若用户已要求并确认无人登录运行，必须验证 `linger=yes`；如未启用且获得对其他服务影响的单独知情授权，才调用已有 user-service CLI 进行 linger 操作。权限不足立即停止并报告，**不得调用 sudo/root**。
4. 执行后调用 `status NAME`，核对 timer `ActiveState/UnitFileState/NextElapseUSecRealtime`、配套 service 状态以及 linger。`logs NAME` 供实际执行后调查。尚未到执行时间时报告「已调度，尚未发生执行」，不能宣称脚本运行成功。
5. 每一步失败时报告哪些文件写入、哪些状态已变更、哪些动作没执行。不得以尝试性 restart、自动补跑、删除重建、吞错或提权当作恢复方案。

## 四个对话例子

### A：只有自然语言要求

用户：「帮我每天凌晨 3 点备份数据库。」
Agent：「你现在通常用什么命令完成数据库备份？可以提供现有脚本路径。」收到命令后只读检查。若目标时区已知，预览 `*-*-* 03:00:00` 的真实下次执行；默认 `Persistent=no`，展示后等待用户确认，不能立即运行备份。

### B：用户给出了全部信息

用户：「`/usr/bin/python3 /home/me/scripts/check.py`，每周一 08:00 跑，叫 `weekly-check`，只创建不要激活。」
Agent：只读检查程序和日历表达式、预览下 3 次执行，不反复询问脚本和服务名；最终确认后只创建 unit，不启动、启用或补跑。

### C：无人登录 + 补跑

用户：「服务器重启我没登录也要执行，漏掉的要补。」
Agent：检查目标用户 linger，说明 `Persistent=yes` 在恢复后可能立刻运行一次，linger 影响该用户其他服务；对具体任务与两项副作用分别取得知情确认，不能把普通「帮我创建」概括为授权。

### D：用户需要修改脚本

用户：「刚才的定时任务改成执行另一个 Python 文件。」
Agent：明确当前 `update` 仅支持 `OnCalendar`、`Persistent`、`AccuracySec`，**目前没有直接修改配套启动程序的功能**；停止此分支，不能擅自删除重建、改写 service 或生成未确认命令。
