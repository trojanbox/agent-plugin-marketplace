# 社区研究对象解析与来源策略

当研究对象有歧义、需要解析账号/仓库/品牌身份，或规划社区来源与补充事实来源时读取。

## Phase 1 — Intent & Time Window

明确：

- 用户关注“评价、使用体验、趋势、争议、比较、发现”中的哪一种；
- 时间窗口；
- 目标语言 / 地区 / 用户群是否有限定；
- 哪些社区最可能出现直接证据；
- 用户真正要做什么决策，例如“要不要采用”“哪个更适合”“值不值得关注”。

不要为了填写模板向用户追问所有字段。已有信息足够时直接研究。

## Phase 2 — Target Resolution

关键词搜索前先解析研究对象。

### 人物

尽量确认：

- 官方姓名 / 常用名；
- 官方社交账号；
- GitHub 用户名（适用于开发者、创始人、研究者等）；
- 相关公司 / 项目；
- 常被讨论的别名或缩写。

### 开源项目 / 软件产品

尽量确认：

- 官方仓库 `owner/repo`；
- 官方产品名与常见简称；
- 官方 docs / release 页面；
- 主要 subreddit、GitHub Issues / Discussions 或社区论坛；
- 容易混淆的同名项目。

### 公司 / 品牌

尽量确认：

- 官网与产品线；
- 官方社交账号；
- 主要社区入口；
- 用户讨论时常用的品牌/产品词。

### 抽象主题

不强行解析账号。改为建立 2～5 组高召回关键词和同义表达。

解析不到时明确按关键词研究，不猜账号、仓库或实体身份。

## Phase 3 — Source Planning

按问题选择来源，不机械搜遍所有平台。

### 优先社区来源

| 来源 | 最适合观察 | 注意事项 |
|---|---|---|
| Reddit | 真实使用体验、长讨论、抱怨、推荐 | subreddit 人群偏差、同温层 |
| Hacker News | 技术/创业社区判断、产品发布讨论 | 技术从业者权重很高，不能代表大众 |
| GitHub Issues / Discussions / PR | 开发者痛点、缺陷、维护活跃度、真实阻塞 | Issue 数量不等于用户规模 |
| YouTube / 视频社区 | 教程采用、创作者评价、长体验 | 标题党与推广内容较多 |
| X / Bluesky / 其他社交平台 | 实时反应、从业者观点、短周期趋势 | 可访问性、机器人、转发与粉丝结构 |
| 专业论坛 / 社群公开页面 | 垂直领域深度经验 | 样本小但可能专业度高 |

### 补充事实来源

需要核验事实时，可读取：

- 官方文档 / release / changelog；
- 项目仓库；
- 公司公告；
- 高质量新闻或专业媒体。

这些资料用于校正“发生了什么”，不能替代社区证据回答“大家怎么看”。

### 可达性原则

只声明当前工具真实能够访问和验证的来源。某个平台无法可靠检索时：

- 不假装已覆盖；
- 使用可访问的搜索索引或公开页面作为有限补充；
- 最终说明缺失的平台及其可能带来的偏差。
