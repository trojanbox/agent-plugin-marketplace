# 社区证据过滤、聚类、比较与趋势发现

收集到原帖后读取，用于去重、相关性过滤、主题聚类、共识/分歧、Comparison/Discovery/人物/项目模式和 Evidence Ledger。

## Phase 4 — Recent Evidence Collection

对每个选定来源做定向检索：

- 时间词使用真实窗口日期；
- 优先获取帖子 / Issue / 讨论的实际发布日期；
- 搜索结果的抓取日期、网页更新时间与事件发生时间要分开；
- 对重要讨论读取原帖和关键评论，而非只看搜索摘要；
- Comparison 模式下，对各候选尽量保持相同时间窗口和来源组合；
- Discovery 模式先广泛发现候选主题，再对候选做第二轮验证，不直接把第一次看到的热门条目当趋势。

每条候选证据至少记录：

- 来源平台；
- 日期；
- 主题 / 观点；
- URL / 可追溯引用；
- 互动或参与信号（若可获得）；
- 是否为独立讨论；
- 与问题的相关性；
- 是否可能是广告、推广、机器人或重复传播。

## Phase 5 — Dedup & Relevance Filter

### 去重

识别并合并：

- 同一原帖的转发 / 引用；
- 同一新闻被多个账号复制；
- 同一发布公告在多个社区形成的“事实重复”。

注意：

**同一事件在多个独立社区产生不同讨论，属于多源反应，不应全部去掉。** 去重的是重复证据，不是跨社区独立观点。

### 相关性过滤

丢弃或降低权重：

- 纯推广 / affiliate；
- 与目标同名但实体错误；
- 无实质内容的 help-me 帖；
- 明显机器人/批量生成内容；
- 超出时间窗口且没有背景价值的旧讨论；
- 只引用别人观点、没有新增信息的二次转述。

## Phase 6 — Signal & Theme Clustering

不要把几十条帖子逐条复述。把独立证据聚成主题。

常见主题类别：

- 高频赞扬；
- 高频抱怨；
- 实际使用场景；
- 迁移 / 放弃原因；
- 竞品比较；
- 新出现的工作流 / 用法；
- 可靠性 / 性能 / 价格 / 学习成本；
- 维护者响应；
- 争议或价值观冲突；
- 新发布带来的短期情绪变化。

### 信号强度

综合考虑：

1. **Relevance**：是否直接回答研究问题；
2. **Recency**：是否位于目标窗口，离当前越近是否更重要；
3. **Independence**：是否来自独立讨论 / 独立用户群；
4. **Engagement**：评论、upvote、likes、stars 等参与度；
5. **Specificity**：是否包含具体案例、数字、复现、迁移经历，而非一句情绪；
6. **Cross-source confirmation**：是否在不同平台出现相似模式。

互动量只作为其中一项，不能压过相关性、独立性和具体证据。

## Phase 7 — Cross-source Validation

对最重要的 3～7 个主题检查：

- 是否出现在多个独立帖子；
- 是否跨平台出现；
- 是否只是一个平台特有文化；
- 是否由某次发布 / 事故 / 价格变化等外部事件驱动；
- 是否能用官方资料确认相关事实背景；
- 反面样本是否存在。

如果某个主题只来自一个强样本，表述为：

> “一个高参与度讨论中出现……”

不要升级成：

> “社区普遍认为……”

## Phase 8 — Consensus / Polarization Check

把结论分为：

### Recurring pattern / 重复模式

多个独立来源反复出现，足以称为“高频观点”或“明显模式”。

### Polarized / 明显分歧

不同群体或平台持续给出相反评价。说明分歧发生在哪些用户群 / 使用场景。

### Weak signal / 弱信号

有少量值得注意的讨论，但样本不足以外推。

### No stable signal / 无稳定信号

窗口内没有足够独立证据形成可靠判断。

除非有可解释、可复现的抽样方法，不输出“73% 用户认为……”这类伪精确社区比例。

## Comparison 模式

比较 A / B / C 时：

1. 使用相同时间窗口；
2. 尽量使用相同来源组合；
3. 分别解析各自官方仓库 / 社区入口；
4. 对每个对象独立收集，再做横向聚类；
5. 比较用户为什么选择、迁移或放弃，而不只比较功能列表；
6. 区分用户群，例如新手、重度用户、开发者、企业团队；
7. 如果 A 的社区规模远大于 B，不能拿绝对帖子数量直接证明 A 口碑更好。

输出推荐时写清：

> 哪类用户更倾向于 A，哪类用户更倾向于 B，以及证据强弱。

## Discovery 模式

研究“最近有什么值得关注”时采用两段式：

### Candidate Discovery

从多个独立社区发现候选主题，优先：

- 短期参与度明显上升；
- 多个平台同时出现；
- 新产品 / 新版本 / 新争议引发真实讨论；
- 有具体使用案例或冲突，而非单纯宣传。

### Candidate Verification

每个候选再做定向检索，确认：

- 讨论发生在目标窗口；
- 有至少两份独立证据，或一份非常强的一手社区证据并明确标记弱验证；
- 能说明“为什么现在值得关注”；
- 没有把营销投放 / 单一爆帖误判为自然趋势。

证据不足时可以输出：

> “当前窗口没有发现足够扎实的新趋势。”

不要为了凑榜单制造候选。

## 项目 / 人物研究

### 开源项目

优先补充：

- latest releases；
- issues / discussions 高频主题；
- 最近 PR / 维护活动；
- GitHub 社区外的 Reddit / HN 反应；
- star、issue 数量等只能作为采用/活跃信号之一。

### 人物

如果身份与主题相关：

- 解析官方社交账号；
- 开发者 / 创始人 / 研究者可解析 GitHub 用户；
- 区分本人发布、媒体转述和第三方评论；
- 本人的帖子用于理解“本人说了什么”，第三方讨论用于研究“社区如何反应”。

## Evidence Ledger

内部维护轻量证据表：

| Theme / Claim | Independent Evidence | Platforms | Window | Signal | Caveat |
|---|---|---|---|---|---|
| 高频抱怨 A | 4 个独立讨论 | Reddit + GitHub | in-window | strong | 偏开发者样本 |
| 新用法 B | 2 个案例 | HN + YouTube | in-window | medium | 样本仍小 |
| “大家都迁移到 C” | 1 个爆帖 | Reddit | in-window | weak | 无跨源验证 |

重要结论必须能回到原始讨论或可靠事实源。

## Exit Gate

满足以下条件即可结束：

- 时间窗口已覆盖；
- 主要目标实体解析正确；
- 核心社区来源已经按问题选择并检索；
- 高频主题有多份独立证据，或被明确降级为弱信号；
- 主要正面、负面和分歧观点都检查过；
- 关键事实背景已必要核验；
- 新一轮检索不再改变主题排序或主要判断；
- 无法覆盖的平台 / 样本偏差已经记录。

如果证据仍稀疏，结束并明确“信号不足”，不要无限扩大时间窗口和平台范围。
