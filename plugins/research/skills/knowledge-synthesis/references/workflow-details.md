# Claim Ledger、聚类、置信度与覆盖检查

正式综合多份材料时读取，用于 Source Inventory、Claim Ledger、语义聚类、置信度、冲突处理和 Exit Gate。

# Workflow

## Phase 1 — Frame the Synthesis

明确：

1. 用户真正要回答的问题；
2. 当前允许使用哪些材料；
3. 是否有时间范围或“当前状态”要求；
4. 用户更关心事实、决策、趋势、观点还是行动项；
5. 输出需要多细。

已有信息足够时直接开始，不重复询问用户已给出的内容。

## Phase 2 — Build a Source Inventory

对重要来源记录最小元数据：

| Field | Meaning |
|---|---|
| Source ID | 可引用/识别的来源 |
| Type | 文档、邮件、聊天、会议记录、网页、数据等 |
| Author / Owner | 已知时记录 |
| Date / Version | 已知时记录 |
| Location | 文件名、频道、线程、URL、标题等 |
| Directness | 原始事实 / 正式决定 / 转述 / 评论 |
| Status | final / draft / historical / unknown 等 |

缺失元数据保持 unknown，不要编造日期、作者或版本。

## Phase 3 — Normalize and Deduplicate

1. 找出明显重复项；
2. 区分原始来源与衍生引用；
3. 选择最完整/最直接版本作为主证据；
4. 合并重复细节；
5. 保留真正独立的 corroboration；
6. 保留不同版本、时间段和不同观点。

## Phase 4 — Build the Claim Ledger

把材料从“文档列表”转成“可判断的 Claim 集合”。

对关键 Claim 至少记录：

- Claim 内容；
- 哪些来源支持；
- 哪些来源反对或限制；
- 时间/版本；
- 是否为直接证据；
- 是否存在独立佐证；
- 当前证据状态。

建议状态：

- `strong`：直接、权威、相互独立的证据充分一致；
- `supported`：有可靠支持，但覆盖或独立性有限；
- `mixed`：存在实质冲突、范围差异或版本不一致；
- `weak`：单一、间接、过旧或上下文不足；
- `unknown`：材料不足以判断。

这些状态是解释工具，不做伪精确的数字打分。

## Phase 5 — Cluster by Meaning, Not Source

围绕用户问题按主题组织，例如：

- 决策；
- 原因；
- 当前状态；
- 风险；
- 反对意见；
- 未决问题；
- 行动项。

不要按“来自邮件 / 来自聊天 / 来自文档”机械排列。来源是证据属性，不是知识结构。

如果时间演进本身很重要，同时建立 chronology。

## Phase 6 — Assess Evidence Confidence

置信度至少考虑五个维度：

### Directness

原始数据、正式决定、第一方声明通常比二手转述更直接。

### Authority

权威性依问题而变化：

- 当前政策：正式政策/规范比聊天讨论高；
- 项目实际状态：真实系统状态、已合并实现或明确完成记录可能比旧规划文档高；
- 社区观点：社区原始讨论本身可能就是一手证据。

不要建立跨所有问题都固定不变的来源排行榜。

### Freshness

时效权重由 Claim 类型决定：

- “现在是什么状态”高度依赖最新信息；
- 历史事件不会因为资料变旧而自动降级；
- 稳定政策/定义的有效性取决于是否已被替代；
- 新来源不能仅凭日期自动覆盖更权威的正式来源。

### Independence

多个独立来源一致，比多个转载同一来源更有价值。

### Agreement and Coverage

看关键证据是否一致，也看是否还有会实质改变结论的空白。

## Phase 7 — Resolve or Preserve Conflicts

对于每个 `mixed` Claim：

1. 对齐对象与范围；
2. 对齐时间和版本；
3. 检查定义/口径；
4. 查原始来源与转述链；
5. 判断是否为历史演进；
6. 若仍冲突，明确保留冲突。

允许最终答案写：

> 当前材料不足以确定唯一结论。

不要通过平均、投票或挑一个更顺眼的来源制造确定性。

## Phase 8 — Coverage and Gap Check

综合前检查：

- [ ] 核心问题是否有材料支撑；
- [ ] 关键 Claim 是否有来源；
- [ ] 重复转载是否没有被误算成独立佐证；
- [ ] 重要版本演进是否被保留；
- [ ] 冲突是否被解释或明确保留；
- [ ] 当前状态与历史/计划是否被区分；
- [ ] 重要未知项是否仍可能改变结论。

如果材料不足：

- 直接说明当前能确定什么；
- 列出会改变结论的关键缺口；
- **不主动扩展研究**。

用户要求补齐缺口时，再进入 `research`。

## Phase 9 — Synthesize

默认输出顺序：

1. **先回答问题**：给出当前材料能支持的核心判断；
2. **按主题综合**：合并多个来源的共同信息；
3. **保留演进**：必要时说明从旧状态到新状态的变化；
4. **冲突 / 不确定性**：只展示会影响判断的重要冲突；
5. **证据归因**：让重要 Claim 能回到来源；
6. **关键缺口**：仅在材料不完整且缺口重要时出现。

使用当前宿主环境原生的 citation / file citation / connector attribution 机制；如果没有原生引用格式，再使用清楚的来源标签。不要为了统一模板破坏宿主要求的引用格式。

# Result-Set Scaling

不要死守固定条数，根据复杂度选择粒度。

### 小型材料集

材料少且彼此差异明显时，可以保留更多细节和逐项上下文。

### 中型材料集

按 2–6 个主题聚类，并给每个主题一个综合判断；不要逐条复述所有来源。

### 大型材料集

优先输出：

- 3–7 个最高价值结论；
- 最重要的冲突或少数派观点；
- 关键时间演进；
- 可追溯的代表性来源；
- 重要证据缺口。

不要为了“覆盖全部”生成一份新的原始结果列表。

# Exit Gate

完成综合需要满足：

- 核心用户问题已经被直接回答；
- 关键 Claim 能追溯到来源；
- 重复和独立佐证被区分；
- 重要分歧和版本演进没有被压平；
- 置信度表达与证据强度匹配；
- 没有用外部常识填充 source-bounded 缺口；
- 剩余缺口已经明确，且继续综合同一批材料不会产生实质新结论。
