# GitHub Incidental Bug Capture / 旁路缺陷捕获

系统消息、项目固定边界和当前用户消息始终优先。共享证据、范围、Issue 边界和安全规则见 `../../shared/github-core/references/collaboration-policy.md`。

## 唯一目标

当另一个研发主任务正在进行时，**不要让已经被当前证据证明的独立 Bug 因为“这轮主要不是在查 Bug”而被忽略**。

典型链路：

```text
调研 / 讨论 / API 审计 / 结论 / 开发计划 / 技术或业务测试方案 / 测试方案审计
        │
        ├─ 发现普通事实 / gap / 技术债 → 留在原主任务
        │
        └─ 发现独立真实 Bug
             → 冻结证据
             → 查重开放 + 已关闭 Issue
             → 复用 / 补充 / 重开 / 新建
             → 返回原主任务继续
```

本 Skill 是**内部旁路组合能力**，`visibility: internal`；它不参与 `list` / `catalog` 的用户主任务候选，只允许被其它 Skill 通过 `uses / optional_uses` 组合加载，或在维护/诊断时按逻辑 ID 直接读取。它不抢走原主 Skill 的任务语义。

---

# 一、何时触发

只有发现项同时满足以下条件时才进入 Bug 捕获：

1. 当前源码/日志/测试/复现证据已经证明存在真实异常行为，或存在确定性代码路径会违反当前已知合同；
2. 目标能力在当前系统中已经存在，不是用户尚未提出的新功能；
3. 该问题可以形成独立复现、独立修复或独立验收边界；
4. 至少能够写出“预期 vs 实际 + 当前证据 + 影响范围”；
5. 不需要先做新的产品/架构决策才能判断“这是不是错的”。

根因可以是：

- `已确认根因`；
- `强证据假设`；
- `待验证根因`。

根因尚未完全确认不等于不能记录 Bug，只要**Bug 本身已经被证据确认**。Issue 中必须如实标记根因状态。

---

# 二、以下内容不能自动报 Bug

不要把这些内容误报为生产 Bug：

- 当前功能根本未实现；
- 用户本轮新提出但尚未批准的需求；
- 目标合同仍在讨论；
- 文档落后但运行链路正确；
- 测试本身写错；
- Harness/环境故障；
- 纯命名、格式、风格问题；
- 没有现实影响的维护性建议；
- 只有“看起来可疑”的代码，没有违反合同或可观察故障证据；
- 需要大量猜测才能成立的问题。

这些发现仍应留在原主任务中，不能“为了不遗漏”把所有问题都变成缺陷 Issue。

---

# 三、与 `github-bug-investigation` 的边界

### 本 Skill

用于：

> “我本来在做别的研发任务，但顺手发现了一个已经有证据的 Bug，立即记录下来，然后继续。”

特点：

- 输入来自当前主任务已经收集的证据；
- 不要求把主任务切换成完整缺陷调查；
- 目标是及时、去重、可追踪地留痕；
- 默认只做旁路查重与留痕；
- 不展开开发实施步骤或测试代码。

### `github-bug-investigation`

用于：

> “这轮主要目标就是查这个 Bug 的根因、影响、复现和验收。”

如果旁路发现项证据还不足，且需要专门深挖才能确认，应记录为当前 Finding，并建议后续进入 `github-bug-investigation`；不能为了自动建 Issue 而编造根因。

---

# 四、一个问题一个 Issue

对候选 Bug 先判断：

- 是否可以独立触发；
- 是否拥有独立根因或修复路径；
- 是否可以独立验收；
- 修复一个后另一个是否仍然存在。

同根因的多个症状合并；不同根因或独立验收的问题拆分。

禁止把“调研过程中发现的所有异常”塞进一张大 Bug。

---

# 五、证据快照

在离开当前上下文前，至少冻结：

- 当前源码基线 / ZIP / commit / workspace；
- 相关文件和符号；
- 触发入口和最小复现条件；
- 预期行为；
- 实际行为；
- 日志/错误/测试/截图/命令等关键证据；
- 根因状态；
- 已知影响；
- 与当前主任务的关系。

不要把当前主任务的全部长报告复制进 Bug。Issue 只保留证明该独立问题所需的最小充分证据，并引用来源调研/讨论/测试 Issue（若存在）。

# 六、查重与生命周期

本 Skill 必需组合：

- `development/github-issue-triage`；
- `development/github-issue-manager`。

顺序固定：

1. 确认目标仓库；
2. 搜索开放 Issue；
3. 搜索已关闭 Issue；
4. 比较根因、触发条件、模块、错误文本和历史验收；
5. 得出：复用 / 补充 / 重开 / 新建 / 暂缓；
6. 再执行写操作。

规则：

- 同一根因已有开放 Issue → 追加新证据；
- 同一根因已关闭但当前复发 → 优先重开并补充新证据；
- 根因或修复边界不同 → 新建并关联历史项；
- 无法完成 GitHub 读取 → 不能声称已查重；
- 无法写入 → 生成标准 handoff；
- 未获得工具成功结果 → 不能声称已创建/更新/重开。

---

# 七、严重级别

沿用统一 Bug 级别：

- `P0`：灾难性影响，需要立即止损或响应，例如核心生产能力大面积不可用、不可逆数据损坏、活跃安全/隐私事件；
- `P1`：核心或关键流程严重受损、影响范围大、存在明显数据/兼容风险；
- `P2`：有明确业务影响、需要正常排期修复的问题，例如部分场景失败、非核心流程异常或存在可接受绕行；
- `P3`：低影响但证据充分的真实缺陷，例如轻微 UI/提示异常、低频边界回归或低影响兼容问题。

严重级别必须由影响证据决定。不能因为问题是“顺手发现”就自动降为 P3，也不能把体验优化、技术债、代码风格、新需求或未决产品选择塞进 P3。

标题格式：

```text
【缺陷】P<0|1|2|3> <可检索故障标题>
```

---

# 八、Issue 最小内容

即使是旁路捕获，也必须包含：

1. Bug 摘要；
2. 严重级别与依据；
3. 环境/基线；
4. 最小复现条件；
5. 预期行为；
6. 实际行为；
7. 根因状态；
8. 当前影响；
9. 涉及文件/符号；
10. 证据；
11. 问题边界；
12. 永久修复方向；
13. 可验证验收标准；
14. 来源主任务 / 关联 Issue。

“永久修复方向”只描述根因级方向，不在这里展开开发计划、测试方案或具体实施步骤。

---

# 九、是否打断原主任务

默认：**记录完 Bug 后继续原主任务**。

只有以下情况阻塞受影响范围：

- P0；
- 安全或隐私风险需要受限处理；
- 继续执行可能扩大数据破坏；
- Bug 会污染后续证据，使当前任务结论不再可信；
- 当前主任务后续步骤必须依赖这个 Bug 先被修复。

即使阻塞局部范围，也继续与该问题无依赖的其它分析。

---

# 十、不默认修复

旁路发现 Bug 不等于用户授权修改生产代码。

- 默认只记录；
- 独立新根因仍应单独建 Bug，并避免未经授权扩大修改；
- 需要拆修复任务时进入 `github-development-plan-generator`；需要设计技术/业务回归时进入对应测试方案 Skill。

禁止顺手吞错、加延时、无限重试、硬编码或绕过校验来“顺便修掉”。

---

# 十一、返回主 Skill 的最小结果

本 Skill 完成后向原主 Skill返回：

```text
Bug capture result
- finding_id:
- decision: reused / supplemented / reopened / created / pending
- issue: #<id> / local handoff id
- severity:
- root_cause_status:
- blocks_main_task: true / false
- reason:
```

原主 Skill 在最终答复中只需要简要列出已记录 Bug，不要让旁路 Issue 抢走主要报告篇幅。

---

# 十二、强制检查

- [ ] 当前发现项确实属于已存在能力的真实 Bug；
- [ ] 未把新需求、合同未决、文档漂移、测试/Harness 问题误报为生产 Bug；
- [ ] 一个问题一个 Issue；
- [ ] 已冻结最小充分证据；
- [ ] 已执行开放 + 已关闭 Issue 查重，或明确标记无法查重；
- [ ] 已根据真实工具结果执行复用/补充/重开/新建，或生成 handoff；
- [ ] 未默认修复生产代码；
- [ ] 非阻断问题记录后已返回原主任务继续。
