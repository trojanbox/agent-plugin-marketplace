# 讨论 Issue 结构与决策记录

在创建/续用【讨论】Issue、追加决策或刷新状态面板时读取。

## 建立或续用讨论 Issue

Issue 正文是当前讨论状态面板，建议按以下结构维护：

```markdown
# 【讨论】<主题>

## 1. 背景与目标

## 2. 范围与非目标

## 3. 证据索引

## 4. 当前实现
### 当前流程图
### 当前时序图

## 5. 当前问题

## 6. 决策树

## 7. 当前待决项

## 8. 已确认决策

## 9. 目标方案
### 目标流程图
### 目标时序图

## 10. 当前实现 → 目标方案差距

## 11. 决策索引

## 12. 未决问题

## 13. 当前状态
- 状态：discussion_in_progress / ready_for_business_test_plan / ready_for_technical_test_plan / ready_for_spec / ready_for_development_plan / blocked
- Spec Gate：required / not_required / undetermined
- Spec Gate 理由：<为什么需要或可以跳过结论>
- Spec 来源/跳过记录：<spec_source / spec_not_required / spec_skipped_by_user>
- 已确认：<数量>
- 部分确认：<数量>
- 延期：<数量>
- 待决项：<数量>
- 未决：<数量>
```

不适用的章节可以省略，但复杂系统讨论不得省略必要的当前实现图 / 目标方案图。

## 决策门与提问方式

遇到会改变产品语义、系统职责、状态所有权、持久化、外部契约、用户体验或交付范围的未决事项时，标记 `DECISION_REQUIRED`，停止受影响设计分支，不替用户选择“合理默认值”。无依赖的调查可以继续。

提问必须从当前待决项中选择。默认一次只问一个最高杠杆决策点；如果多个 待决项 节点简单且强耦合，可以小批量提问，但每项必须能独立回答。不要跨过尚未解决的前置节点，也不要把多个重大决策塞进一个问题。

每个决策问题应包含：

- `Q-xxx` 节点编号；
- 决策背景；
- 为什么现在需要决定；
- 2～4 个具体可执行选项（确有必要时）；
- 各选项对范围、兼容、数据、体验、测试或运维的影响；
- **模型推荐答案及依据**；
- 可自由补充的入口。

### 推荐答案规则

原则上**每一个决策问题都必须给出推荐答案**，降低用户重复承担方案筛选成本。推荐必须满足：

1. 依据当前源码事实、已确认 `D-xxx`、用户约束和已验证证据；
2. 明确说明推荐理由和关键权衡；
3. 推荐只是建议，用户未确认前不得进入目标方案或写成最终决定；
4. 如果证据不足以可靠排序选项，不编造推荐，明确写 `暂不推荐`，说明缺少什么事实，并优先调查能自行验证的事实；
5. 纯偏好型产品取舍如果没有客观最优解，也要给出基于当前目标的倾向性推荐；只有确实无法形成负责任建议时才使用 `暂不推荐`。

不要为了格式强行凑 2～4 个选项。存在明显主方案时可以直接给“推荐方案 + 可行替代”，重点是让用户能够清楚确认或否决。

## 用户回答后的处理

### 1. 分类和确认

把回答拆分并明确标识：

- `事实`：用户补充的当前真实约束或业务事实；
- `决定`：用户本轮明确选择；
- `推断`：根据证据做出的可解释推断；
- `假设`：尚待源码/运行结果验证；
- `延期`：明确留到以后处理；
- `非目标`：本轮明确不做。

只有存在会改变实际结论的实质歧义时才继续追问。

### 2. 追加决策评论

每条重大决定使用独立 `D-xxx` 记录：

```markdown
## 决策记录 D-<序号>：<决策点>
- 状态：已确认 / 部分确认 / 延期 / 否决 / 已被替代
- 用户选择：
- 选择理由：
- 被否决方案及原因：
- 下游开发/测试约束：
- 影响范围：
- 当前实现影响：
- 目标方案影响：
- 仍未决：
- 来源证据：E-xxx / 用户确认
- depends_on：D-xxx / 无
- supersedes：D-xxx / 无
```

用户原话可短引用，主体使用准确释义。

### 3. 处理依赖和替代

- 后续决定依赖之前决定：填写 `depends_on`；
- 后续决定推翻之前决定：新决定填写 `supersedes`，旧决定状态改为“已被替代”；
- 不删除旧评论，不改写历史；
- 正文只展示当前有效决定和最新目标方案。

### 4. 刷新状态面板

用户每次确认重大决定后，根据影响程度更新：

- 已确认决策；
- 决策索引；
- 决策树节点状态、依赖和 `D-xxx` 引用；
- 当前待决项；
- 当前实现 / 目标方案 / 差距；
- 目标流程图 / 目标时序图；
- 未决项；
- 当前状态。

如果决定不改变调用链、职责、状态、顺序或异常语义，可以不重画图。

## 讨论就绪检查

准备结束讨论前检查：

- 本轮目标和非目标是否明确；
- 决策树是否覆盖目标范围内已知重大决策及其依赖；
- 待决项是否为空；若为空，是否确认没有漏建节点、错误剪枝或阻塞中的事实调查；
- 当前实现是否有足够证据；
- 目标方案是否只包含已确认决定；
- 当前实现与目标方案是否存在未解释的差距；
- 状态所有权和推进时机是否明确（如适用）；
- 成功路径、失败路径、恢复/退出条件是否明确（如适用）；
- 数据写入和关键副作用的时机是否明确（如适用）；
- 对外部服务、兼容性和边界条件是否有未决阻塞项；
- 决策树、待决项、流程图、时序图、正文和决策评论是否一致；
- 所有可由 Mermaid 清晰表达的图是否已经使用 Mermaid；若使用文本图，是否确有不适合 Mermaid 的理由；
- 是否存在相互冲突、已失效但未标记的决定；
- 测试和验收是否至少能从目标行为中推导出来；
- 延期项是否真的不阻塞本轮讨论收口和目标下游交付物。

存在阻塞项时继续讨论，不要为了“结束流程”强行宣布讨论已收口。
