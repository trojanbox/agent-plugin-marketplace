# GitHub 结论

## 产品阶段边界

明确【开发·结论】或技术合同冻结由本 Skill 主导；独立产品 PRD/用户场景/行为与验收的需求结论归 `product/product-conclusion`。用户只说“结论”时先用当前对话权威阶段判断，确有不同主交付物才澄清；不因新增 Product 改写已确认的研发决定。

## 唯一目标

把已确认的目标行为写成一份**独立可转发、通俗易读且技术合同完整**的【开发·结论】Issue。收件人无需阅读讨论 Issue 或评论就能理解目标、流程、边界及验收；结论继承决定的**内容**，但正文不引用或链接任何原始讨论材料。

共享研发规则见 `../../shared/github-core/references/collaboration-policy.md`。

## Skill Composition / 旁路缺陷捕获

- 需要 GitHub 持久化时组合 `github/github-issue-manager`，使用其查重、写入恢复与 handoff 协议；本 Skill 保留研发内容与阶段 Gate，不复制通用远端操作。

整理结论时若证据中确认独立生产 Bug，组合 `development/github-incidental-bug-capture` 查重留痕；缺口、未决合同、测试问题不能伪装成 Bug。

## 明确创建授权 Gate（强制）

在阅读来源、生成独立规格或写入结论 Issue **之前**，核对用户已明确要求创建/生成本轮【开发·结论】（也允许前文仍有效的明确预授权）。**“讨论完了”“能否收口形成结论”“Spec Gate=required”“开发计划需要结论”均不构成创建授权。**

- 没有明确授权：只告知结论已经就绪、询问“是否现在创建”，停留于 `development/github-discussion-facilitator` / `ready_for_spec`；不得自行生成正式结论正文、创建/更新 Issue、关闭讨论或将 `ready_for_spec` 冒充 `spec_source`。
- 用户明确答应或直接要求创建：按真实来源执行现有完整性与查重流程；用户指定只起草本地预览时不得写入 GitHub。
- 用户明确跳过结论与用户明确要求创建是**两个不同的授权**，不能混用。

## Spec Gate

- `required`：API/数据/事件/状态生命周期/模块职责/安全/失败恢复/并发/幂等/跨服务职责等高传播合同变化，需要当前有效【开发·结论】。
- `not_required`：局部低传播、已有合同内直接修正，可记录理由后跳过。
- `undetermined`：会改变最终产品/API/数据/安全合同的关键事实或决定仍缺失，返回调研/讨论。
- **开发结论不以 E2E、真实外部联调或文件容量实测已经通过为默认前提**。合同已确认时可以在结论中标出未验证事实及后续验收门槛；只有关键事实缺失已使最终方案无法成立或无法选择时才阻塞冻结。

用户明确点名【开发·实施计划】（开发计划）、【开发·业务测试】（业务测试方案）或【开发·技术测试】（技术测试方案）时，由对应下游 Skill 先承接并执行 Gate；进入 `ready_for_spec` 后**先征得结论创建授权**，再转本 Skill。用户明确要求“生成/创建结论/规格冻结”时，本 Skill 主导。

## 核心流程

1. **读取完整来源**：当前讨论、用户确认、源码证据、相关历史记录；建立当前有效来源集。
2. **覆盖核对**：生成正文前读取 `references/source-and-integrity.md`，确保所有已确认决定和关键合同无损继承，过期来源不继续当权威。
3. **人话总结 + 完整合同**：正文第一部分用通俗语言说明背景、目标、最终方案与用户体验；第二部分完整自包含地展开 API/数据/状态/失败恢复/安全/兼容；第三部分给出验收标准和实施边界。**正文不附任何来源/关联 Issue/讨论评论链接、历史编号跳转、`见上文` 或依赖读者跳到其它文档才明白的描述；API 合同中的正常 URL 示例是业务字段，不属于来源引用。** 未确认内容保持未决，不自行补齐。
4. **旁路缺陷**：发现独立生产 Bug 时使用旁路捕获，不把缺陷修复细节混进结论合同。
5. **写入与交接**：需要 GitHub 生命周期、Issue 结构、查重或下游衔接时读取 `references/delivery-and-issue.md`。
6. **写后审计**：内部检查来源→结论、结论→来源、图文、跨 Issue 一致性，并检查独立可读性与正文零讨论链接；这些内部追溯核对结果不附在结论正文里。关键项缺失时不得宣布完成。

## 完成状态

只有真实写入成功且完整性检查通过时，才能说【开发·结论】已创建/更新。结论完成只代表目标合同被冻结，不代表实施或测试已经完成。
