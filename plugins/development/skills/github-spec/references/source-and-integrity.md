# 结论来源、覆盖与完整性检查

在生成【结论】正文前读取，用于建立有效来源集、覆盖表、无损继承关键合同和写后完整性检查。

## 第一步：完整读取来源

### 1.1 必须读取的来源

至少包括：

- 原讨论 Issue 的当前正文（如果存在）；
- 原讨论 Issue 的全部决策评论和事实补充（如果存在）；
- 用户当前补充说明；
- 用户提供的需求、设计、会议记录、截图或附件；
- 当前源码、配置、测试和文档；
- 相关历史 Issue、架构决策记录或约束；
- 上游已经确认、且本轮明确继承的结论；
- 没有正式讨论 Issue 时，用户明确确认的需求、决定、接口清单或其他冻结来源。

如果 GitHub 返回内容被截断，必须继续读取、搜索或分页，直到能确认所有当前有效决定、事实、延期项和验收要求都已覆盖。不能只根据搜索摘要或前几条评论生成结论。

### 1.2 来源状态

对每项来源内容标记状态：

- **已确认决定**：可以进入最终方案；
- **事实证据**：有源码或直接材料证明；
- **推断/假设**：必须显式标记，不能伪装成事实；
- **被替代**：保留历史追溯，不进入当前目标方案；
- **延期/非目标**：保留边界，但不纳入本轮交付；
- **冲突**：必须先解决，不能同时进入结论。

源码只能证明当前实现，不能替代产品决定；讨论决定也不能伪装成已实现事实。

## 第二步：建立“有效来源集”

在写结论之前，先把本轮所有当前有效的重要信息抽成稳定条目。至少覆盖以下类型：

1. **决定**：最终选择、理由、被否决方案；
2. **事实**：当前源码、现有运行行为、当前限制；
3. **目标约束**：最终必须满足的职责、状态、接口、失败语义；
4. **流程分支**：主路径、默认路径、失败/回退路径；
5. **接口与数据合同**：接口、DTO、事件、状态、字段、文件归属；
6. **安全边界**：权限、校验、信任来源、禁止行为；
7. **当前到目标的差距**；
8. **验收条件**；
9. **风险与应对**；
10. **延期项与非目标**；
11. **被替代的旧方案**，用于防止后续误用。

来源本身已经有 `D-xxx`、`E-xxx`、`G-xxx`、验收编号时优先沿用，不随意重新编号。

## 第三步：建立“覆盖核对表”

在生成结论正文前，必须建立内部覆盖核对表。最少包含：

| 来源条目 | 类型 | 当前状态 | 必须进入结论？ | 结论落点 |
|---|---|---|---|---|
| D-001 | 决定 | 已确认 | 是 | §X |
| E-004 | 事实 | 有效 | 是 | §Y |
| G-003 | 差距 | 有效 | 是 | §Z |
| A-06 | 验收 | 已确认 | 是 | §N |

规则：

- 所有“必须进入结论”的重要条目都必须有明确落点；
- 任何重要条目处于“未映射”状态时，禁止宣布结论完成；
- 被替代方案不进入目标方案，但要在“被替代方案 / 历史边界”中留下追溯；
- 延期项和非目标必须有明确落点，防止下游计划阶段被重新发散。

这个核对表主要用于结论质量控制，可以不原样写入最终 Issue；但最终回复应能说明已完成覆盖检查。

## 第四步：关键契约必须无损继承

### 4.1 禁止摘要丢项

以下内容只要上游已经明确冻结，就不能为了简洁压缩成模糊表述：

- 接口 / RPC / endpoint 列表；
- DTO / 字段 / enum / error code；
- 事件 / message / callback 列表；
- 状态 / 生命周期状态；
- 文件路径、源码 owner、写回边界；
- 权限与安全校验；
- 回退 / fail-open / fail-closed 语义；
- 幂等、并发、锁、CAS；
- 受影响的读接口和写接口；
- 验收用例和测试矩阵；
- 明确列出的非目标与禁止项。

例如上游已经明确：

```text
initialize
get-document
details
style-context
source-location
execute
events
```

结论不能把它压缩成“相关接口”或“document / operation”。必须逐项继承，除非用户随后明确缩减范围。

### 4.2 可以压缩的内容

可以压缩：

- 重复论证；
- 已被替代且无长期价值的探索过程；
- 多条表达相同含义的重复评论；
- 纯沟通过程中的语气、来回确认。

压缩后不能改变决定、边界、依赖、失败语义或验收范围。

## 第五步：图表完整性检查

如果来源讨论已经形成有效流程图、时序图和“当前到目标的差距”：

- 结论必须继承其语义；
- 没有新决定时，不重新设计成另一套方案；
- 最终标题优先使用“最终流程图”“最终时序图”“当前到目标的差距”；
- 保留来源 `D-xxx` / `E-xxx` 追溯；
- 图与正文、决定冲突时必须修正；
- 如果修图需要新增业务选择，停止生成结论并回到讨论；
- 如果只是把已经确认的分支、失败路径、默认路径补进图中，可以直接补齐，不视为新增设计。

最终流程图至少检查：

- 是否覆盖所有合法入口 / 源码契约分支；
- 是否覆盖默认值；
- 是否覆盖非法输入 / 回退；
- 是否覆盖状态切换；
- 是否覆盖关键失败恢复；
- 是否把“保持不变”的 直接组合 / 既有路径 错误遗漏；
- 是否与验收矩阵表达同一套语义。

跨模块、跨服务、状态推进、异步、外部系统或失败恢复场景，必须保留对应流程图或时序图。

## 第六步：跨 Issue 权威性与过期检查

结论不能只“引用历史 Issue”，还必须判断这些来源现在是否仍然有效。

检查：

- 是否存在旧讨论仍把已收口合同写成“待定”；
- 是否存在旧结论保留了已经被本轮替代的术语、接口或流程；
- 是否存在多个 Issue 对同一子范围给出不同当前结论；
- 是否存在同一术语在不同 Issue 中已经发生含义变化。

如果发现过期冲突：

1. 在新结论中明确“权威范围”和“覆盖关系”；
2. 列出被覆盖的旧表述或旧合同；
3. 所有下游计划必须以最新专项结论为准；
4. 有 GitHub 写入能力时，优先向旧结论追加一条简短追溯评论，说明对应子范围已由新 `【结论】` 覆盖；
5. 不为了“看起来整洁”直接删除历史讨论或抹掉旧决定。

如果无法判断哪个结论权威，停止生成结论并返回讨论层。

## 第七步：生成完整结论

最终方案按实际范围覆盖适用项：

1. 结论信息、来源和权威性；
2. 背景与目标；
3. 最终范围、非目标；
4. 当前实现事实；
5. 最终方案与职责边界；
6. 接口、数据、状态、文件归属和安全合同；
7. 最终流程图 / 最终时序图；
8. 当前到目标的差距；
9. 最终决定记录；
10. 验收标准 / 验收矩阵；
11. 风险与应对；
12. 实施依赖与边界；
13. 复杂度；
14. 延期项；
15. 追溯关系；
16. 真实性边界。

不适用章节说明原因，不用空模板占位。

## 第八步：写后完整性检查

创建或更新 GitHub Issue 后，必须重新读取真实 Issue 内容，然后执行一次双向完整性检查。

### 8.1 来源 → 结论覆盖检查

逐项检查有效来源集：

```text
来源条目
→ 是否进入结论？
→ 结论位置是否准确？
→ 是否被错误压缩？
→ 是否改变了原决定含义？
```

发现遗漏时：

- 直接修正结论 Issue；
- 再次读取；
- 重新执行覆盖检查。

不能先告诉用户“结论已完成”，再等用户二次检查才发现缺项。

### 8.2 结论 → 来源反向检查

逐项检查最终 Issue 中的关键目标内容：

- 是否能在来源中找到决定或证据；
- 是否把建议写成已经确认；
- 是否自行引入上游不存在的新系统、新状态、新接口、新权限或新异常语义；
- 是否把计划中的实现写成已完成。

### 8.3 图文一致性检查

确认：

- 图与正文一致；
- 图与决定一致；
- 图与验收矩阵一致；
- 默认 / 回退 / 失败路径没有缺失；
- 已被替代方案没有以当前路径重新出现。

### 8.4 跨 Issue 一致性检查

确认：

- 新结论已经声明权威范围；
- 旧 Issue 的过期表述不会覆盖新结论；
- 必要的追溯评论已经添加，或明确记录尚未添加的原因。

### 8.5 完成门

只有以下条件全部通过，才能将结果描述为“结论已完成”：

- 有效来源集中的所有重要条目都已映射；
- 关键契约没有摘要丢项；
- 当前方案、决定、图、差距和验收一致；
- 延期项与非目标没有丢失；
- 没有未解决的权威冲突；
- GitHub Issue 已重新读取并通过写后复核；
- 仓库、Issue 编号、标题、标签、正文均真实核对成功。

如果任一项失败，状态应为“结论完整性检查未通过”，不能声称结论已完成。
