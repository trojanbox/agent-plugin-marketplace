# 结论 Issue 结构、查重与阶段衔接

在需要创建/更新【开发·结论】Issue、记录决策或衔接下游计划时读取。

## 决策记录

每个重要决定至少记录：

- 问题；
- 最终选择；
- 选择理由；
- 被否决方案及原因；
- 影响范围；
- 该决定在当前方案中具体解决的约束。

只保留最终有效规则，用完整的人话解释选择理由；旧讨论的编号、来源和链接只用于内部核对。不要只保留结论，也不要把历史比较过程大量搬进正文。

## 复杂度与工时（按需）

默认给出轻量复杂度档位 `S / M / L` 和主要依据：

- `S`：局部、低传播、无数据/外部契约/复杂生命周期；
- `M`：常规跨文件或跨层；
- `L`：跨模块/服务、数据迁移、状态机、并发、外部契约或高风险变更。

不要为了模板完整制造迁移、可观测性、发布或回滚工作。只有用户明确询问工时、进入排期，或工时本身是本轮结论目标时，才给工程小时/人日区间。需要估算时说明前提、排除项和不确定性，区分工作量与日历等待；不写虚假精确值或承诺日期。

## Issue 结构

标题：

```text
【开发·结论】<清晰、可检索的主题>
```

正文按阅读体验分三层，**独立完整，转发即能读懂**：

1. **给人看的摘要**：用自然语言说明为什么做、做成后是什么样、最终方案、适用范围与明确不做的内容；
2. **给研发看的完整合同**：当前实现与改造差距，流程/时序图（适用时），全部接口方法/路径/头/请求与响应示例、数据和状态规则、鉴权、安全、失败/恢复、兼容；
3. **给交付看的边界**：可验证验收标准、重要风险、真实环境依赖、复杂度与延期项（仅适用项）。

**硬性约束**：结论正文不添加任何来源引用、关联 Issue、原始讨论或评论的跳转链接，也不添加 D/E 编号索引与追溯章节；不能用“见 #123”“沿用 D-xxx”“详见上面的讨论”代替本 Issue 的合同全文。来源可在撰稿时内部核对；需要双向追溯时只在旧讨论 Issue 留一条指向最终结论的评论，避免让结论读者依赖旧讨论。

## 查重与创建

此处所有“创建/更新【开发·结论】”操作都必须先通过主 Skill 的**明确用户创建授权 Gate**。当前状态 `ready_for_spec`、历史讨论结束、用户仅问“能否形成结论”不满足授权。只允许在用户明确要求的创建/生成（或有效预授权）范围内执行本节查重和写入；单纯收口只能记录 `ready_for_spec` 并先询问。

查重指纹至少包含：

- 讨论来源；
- 最终目标；
- 关键决定；
- 核心模块；
- 版本 / 快照（如果适用）。

规则：

- 同一轮结论已存在：不要重复创建，优先更新现有结论；
- 只是历史讨论或过期结论：可以创建本轮新结论；从历史读取有效内容后**完整重写在本结论内，不添加历史讨论链接**；
- 目标不同：分别创建结论；
- 已有更大范围上位结论，但当前是不同子范围专项结论：可以独立创建，并明确权威范围。

创建后必须核对编号、URL、仓库、标题、标签和正文完整性。工具失败时不能声称成功。

## 与其他 Skill 的衔接

推荐链路：

```text
源码 / 证据调查
→ 【开发·讨论】决定冻结
→ 【开发·结论】明确目标行为与验收边界
→ 根据目标生成【开发·实施计划】/【开发·业务测试】/【开发·技术测试】
→ 下游 Coding/Test Agent 在真实环境执行（本 Runtime 外）
→ 执行证据返回后继续调研 / 缺陷调查 / 测试方案审计
```

- **本次结论范围内**仍有实质性产品或技术合同未决：回到 `github-discussion-facilitator`；其它明确延期的范围，以及可被写成后续验收义务的真实环境/E2E 未测项，不阻塞当前已确认合同结论；
- 需要实施计划：使用 `github-development-plan-generator`；
- 需要业务测试方案：使用 `github-business-test-plan-generator`；
- 需要技术测试方案：使用 `github-technical-test-plan-generator`；
- 生成结论时旁路发现已确认的独立生产缺陷：组合 `github-incidental-bug-capture` 完成查重与留痕，不把缺陷混入结论；只有用户主目标转为完整根因调查时才使用 `github-bug-investigation`。

## 真实性边界

明确区分：

- **已完成**：来源读取、证据复核、覆盖核对、结论 Issue 创建/更新、写后完整性检查；
- **未完成**：实施计划/测试方案（除非本轮另外生成）、代码修改、测试执行、迁移、发布；
- **尚待下游执行确认**：环境相关或仍需真实 Coding/Test Agent 探测的细节。

没有 GitHub 工具成功结果时，不能声称 Issue 已创建或更新；没有重新读取并通过结论完整性检查时，不能声称“结论已完成”。
