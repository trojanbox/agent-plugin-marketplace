# 调研持久化、GitHub 留痕与发布前审计

仅在用户明确要求 Markdown/Wiki/GitHub 留痕，或准备发布持久化调研产物时读取。

# 七、Markdown 文件生成

## 1. 路径

统一生成到：

```text
/mnt/data/research-docs/<slug>.md
```

`slug` 使用简洁、稳定、可读的英文或拼音短横线命名。文件正文 H1 使用：

```markdown
# 【调研】<主题>
```

## 2. 元数据

开头至少包含：

```markdown
| 元数据 | 内容 |
|---|---|
| 调研主题 | ... |
| 源码/需求基线 | ... |
| 基线 SHA/HEAD | ... |
| 调研日期 | YYYY-MM-DD |
| 调研范围 | ... |
| 验证方式 | 静态源码 / 测试源码 / 运行验证 / 外部调研 |
```

## 3. 文件真实性

生成后至少执行：

- 文件存在检查；
- 非空检查；
- Markdown fence 成对检查；
- Mermaid fence 成对检查；
- 引用闭环检查；
- 文末 References 存在；
- SHA-256 计算。

如果环境有 Markdown/Mermaid validator，可以继续验证；没有 validator 时不得声称渲染已通过。

# 八、GitHub Issue 写入

## 1. 标题

Issue 标题必须：

```text
【调研】<主题>
```

不能使用 `【讨论】`、`【实施计划】` 或 `【缺陷】` 前缀替代。

## 2. 先查重

调研文档不属于讨论类豁免，创建前必须搜索目标仓库开放和已关闭 Issue。

判断：

- 同一主题 + 同一调研目标 + 同一源码基线，且已有开放 Issue：复用并更新；
- 同一文档的纠错/补充，历史 Issue 已关闭但仍是同一基线：优先重开并更新；
- 同一主题但源码基线/调研轮次已经明显变化：创建新 `【调研】` Issue，并关联历史文档；
- 只有标题相似、实际调研问题不同：新建。

不能因为“以前研究过类似内容”就覆盖历史研究快照。

## 3. 以本地 Markdown 为单一内容源

必须先生成 `.md`，再从该文件内容写入 Issue，避免“下载文件”和“GitHub 内容”出现两套事实版本。

Issue 正文开头追加文件校验信息：

```markdown
> 文档 SHA-256：`...`
> 源码/需求基线：`...`
```

## 4. 超长文档

如果 GitHub 工具/接口无法一次写入完整正文：

1. 本地 `.md` 仍保存完整内容并作为 canonical artifact；
2. 同一个 Issue 正文保存元数据、摘要、目录和分段索引；
3. 按原章节顺序把剩余正文追加为评论；
4. 不得删减章节来适应长度；
5. `参考文献与证据` 必须作为最后一段/最后一条评论写入；
6. Issue 中必须能完整重建本地文档内容。

## 5. 标签

不擅自创建标签。只有仓库已经存在且语义明确的 `documentation` / `research` / 项目指定标签时才可以添加；没有合适标签就不加，并如实说明。

## 6. GitHub 能力降级

执行前确认当前模型是否具备目标仓库的 Issue 读取和写入能力。

- 无读取：不能声称完成查重；生成 triage handoff；
- 无写入：完整生成 `.md`，并生成标准 Issue handoff；
- 有读取无写入：完成真实查重后生成待同步 handoff；
- 交接完成后告知用户切换到具备 GitHub Issues 读写能力的模型，并使用 `github-issue-handoff-sync`；
- 同步前仍必须重新查重。

任何远端写操作只有在 GitHub 工具真实返回成功后才能声称完成。

# 旁路发现的问题（强制）

所有调研输出都必须包含一个 `旁路发现的问题` 小节；即使没有发现问题，也写明“本轮未发现需要旁路留痕的问题”。`documented_research` 时该小节同时进入 Markdown 文档。

对每个发现至少记录：

| 字段 | 要求 |
|---|---|
| `finding` | 一句话描述观察到的问题 |
| `classification` | `已确认 Bug` / `疑似问题待验证` / `非 Bug 缺口` |
| `evidence` | 支撑当前分类的源码、测试、日志、截图或运行证据 |
| `bug_capture` | 已确认 Bug 填 `reused / supplemented / reopened / created / pending` 与 Issue/Handoff；其它类型填 `not_applicable` |
| `impact_on_research` | 是否阻塞或污染本轮调研结论 |

规则：

- 已确认 Bug：必须先通过内部 `github-incidental-bug-capture` 查重和留痕，再写入这里；
- 疑似问题待验证：明确还缺什么证据，不得为了自动报 Bug 把猜测写成事实；
- 非 Bug 缺口：例如未实现能力、合同未决或文档漂移，按真实类别记录；
- 旁路发现不替代主调研结论，记录后继续原调研。

# 九、发布前完整性审计

文档和 Issue 写入前逐项检查：

## 来源覆盖检查

- [ ] 已读取适用 `AGENTS.md`；
- [ ] 已记录源码/附件基线；
- [ ] 重要入口、类型、规则、调用方、消费者都完成搜索；
- [ ] 当前实现没有用历史 Issue/文档替代源码；
- [ ] 未检查范围已明确列出。

## 结论覆盖检查

- [ ] 每个非平凡事实有引用；
- [ ] 每个数字/阈值有引用；
- [ ] 每张事实表每行有证据列或明确引用；
- [ ] 每个图有证据映射；
- [ ] 每个差距项 同时有需求/定义证据和当前源码证据；
- [ ] 每个推断明确标记为推断；
- [ ] 无证据内容标为待验证，没有补造事实。

## 引用闭环检查

- [ ] 正文每个 `[N]` 都能在文末 References 找到；
- [ ] References 中不存在无法定位的“来源：源码”泛化描述；
- [ ] 路径、symbol、Issue 编号、附件名可定位；
- [ ] 引用实际支持正文，不扩大解释；
- [ ] 同一来源可复用编号，避免人为制造大量重复引用。

## 结构与可读性检查

- [ ] 概念先定义，流程后展开；
- [ ] 入口→输入→处理→输出→失败→缺口顺序清楚；
- [ ] 没有在早期章节突然引用尚未介绍的内部概念；
- [ ] Mermaid 能表达的图已经使用 Mermaid；
- [ ] 复杂跨服务流程包含时序图；
- [ ] 文档完整，没有人为 Top-N 截断重点。

## 真实性检查

- [ ] 调研过程中发现的异常/疑似问题没有被静默忽略；
- [ ] 当前调研输出包含“旁路发现的问题”小节；`documented_research` 时文档也包含该小节；已确认 Bug 有真实查重/留痕结果或明确 pending/handoff；
- [ ] 没运行的测试没有写“已通过”；
- [ ] 没创建成功的 Issue 没写“已创建”；
- [ ] 当前不存在的能力明确指出“未实现/未闭环”；
- [ ] 计划或建议没有写成当前事实。

任何硬检查不满足时，`analysis_only` 不得称为“完整调研结论”，`documented_research` 不得称为“完整调研文档”。

# 十、参考文献与证据格式

正文末尾必须是最后一个主章节：

```markdown
## 参考文献与证据

[1] **[源码]** `packages/example/src/foo.ts`，symbol：`FooService.run()`，基线：`<sha/head>`。支持：服务入口调用 `run()` 并把结果交给 `BarService`。

[2] **[需求]** 用户确认，2026-08-17。支持：文档必须生成 Markdown 并写入 `【调研】` Issue。

[3] **[测试]** `packages/example/src/foo.test.ts`，test：`restores completed steps after restart`。支持：重启恢复不重复执行已完成步骤。

[4] **[Issue]** `#123`，章节：`最终决定`。支持：目标状态所有权由后端负责。
```

要求：

- `支持` 只写该来源实际证明的事实；
- 源码优先写 `path + symbol`，行号可附加但不能只依赖行号；
- 用户需求写“用户确认 + 日期 + 支持内容”，不要伪造外部链接；
- 外部网页只有用户要求外部调研时才使用，并记录访问日期；
- References 中包含敏感数据时必须脱敏。
