# 证据基线与源码调研方法

仅在需要建立跨文件/跨模块事实基线时读取；引用格式使用主 `SKILL.md` 已声明的 citation style。

# 一、启动条件

## 1. 明确调研问题

开始前从用户请求中提取：

- 调研主题；
- 用户真正想回答的问题；
- 目标系统/模块；
- 时间或版本范围；
- 需要重点关注的维度；
- 明确非目标。

如果用户已经给出足够材料，不重复询问已知信息。材料不完整时先完成能够由当前证据支持的部分，并把缺口写入“待验证项”；不得为了让文档看起来完整而猜测。

## 2. 源码优先

涉及当前实现时：

1. 先检查当前会话上传文件和 `/mnt/data`；
2. 访问项目源码前必须读取根目录及适用子目录 `AGENTS.md`；
3. 再按 `AGENTS.md` 要求读取相关文档索引/专项 Skill；
4. 以当前源码、测试、配置为最终实现依据；
5. GitHub Issue、历史文档可以补背景，不能替代当前源码。

不得从公共 GitHub、搜索引擎或未知镜像拉取项目源码来替代用户提供的源码。

## 3. 冻结证据基线

调研开始时记录至少一个稳定基线：

- 上传 ZIP：文件名 + SHA-256；
- Git 工作区：仓库根 + branch + HEAD + dirty 状态（仅已有工作区可用时）；
- Patch：patch 文件 SHA-256 + 对应基线；
- 单独附件：文件名 + SHA-256（适用时）。

文档中所有“当前实现”结论都默认绑定到这次基线，避免后续源码变化后失去语境。

# 二、证据与引用体系

详细格式使用主 `SKILL.md` 已声明的 citation style。

## 1. 证据优先级

### 当前实现

必须至少由以下之一直接支持：

1. 当前源码；
2. 当前测试源码；
3. 当前配置/schema/migration；
4. 可复现运行日志或命令结果（只能证明实际观测到的行为）。

项目文档、Issue 或历史讨论只能补充，不得在与当前源码冲突时覆盖源码。

### 目标需求

必须至少由以下之一直接支持：

1. 用户当前明确要求；
2. 用户已确认的历史决定；
3. 已确认 PRD / 需求文档；
4. 已冻结的 `【讨论】` / `【结论】` 决策。

未经确认的建议不能写成目标需求。

## 2. 论文式编号引用

正文只使用短编号：

```text
[1]
[2]
[3][4]
```

完整引用信息统一放在文档末尾 `参考文献与证据` 中。

推荐类型：

- `[源码]`
- `[测试]`
- `[需求]`
- `[用户确认]`
- `[配置]`
- `[日志]`
- `[Issue]`
- `[项目文档]`
- `[截图]`
- `[外部资料]`（仅用户要求外部调研时）

## 3. “每一项有支撑”的硬规则

以下内容必须带证据：

- 每个非平凡事实段落；
- 每个“当前实现”结论；
- 每个 API、字段、状态、模块职责和调用关系；
- 每个数字、阈值、数量、超时、并发数；
- 每张事实表中的每一行，优先增加 `证据` 列；
- 每个 Mermaid 图中的有业务意义节点和边；
- 每个缺口/问题判断；
- 每个当前能力成熟度结论。

如果一段包含多个独立事实，不能只在段尾放一个并不覆盖全部事实的引用。必要时拆段或为不同事实分别引用。

## 4. 推断必须显式标识

证据能够支持方向、但没有直接写出结论时：

```markdown
**推断：** <结论>。[3][7]
```

不得把推断改写成“源码明确说明”。

## 5. 待验证

没有足够证据时：

```markdown
**待验证：** 当前材料不足以确认 <问题>。现有材料只能证明 <已知事实>。[8]
```

禁止使用经验、常识或模型记忆补齐。

# 三、调研方法

## 1. 先建来源清单

在私下工作区建立来源清单，至少记录：

- Source ID；
- 类型；
- 文件/Issue/附件；
- 精确位置（优先 `路径 + symbol/section`，行号只作为快照辅助）；
- 该来源实际能证明什么；
- 是否 当前实现 / 需求定义 / 补充来源；
- 状态：`verified / partial / pending`。

不要先写长文再倒推引用。先建立证据，再写结论。

## 2. 沿依赖顺序阅读

调研顺序默认遵循：

```text
入口 / 用户触发
→ 输入合同
→ 参数解析 / 校验
→ 核心编排
→ 领域规则
→ 外部依赖 / 工具
→ 数据存储 / 状态
→ 输出合同
→ 失败与恢复
→ 测试
→ 当前缺口
```

如果系统实际结构不同，可以调整，但文档必须让读者能从“为什么存在”自然读到“如何运行”和“输出什么”，不能在没有定义概念时直接跳到深层实现。

## 3. 搜索必须覆盖传播链

对关键 ID、类型、接口、字段、事件、表、配置、Agent、Workflow 名称执行仓库级搜索，确认：

- 定义在哪里；
- 谁生产；
- 谁消费；
- 是否持久化；
- 是否进入 Prompt / API / DB；
- 是否存在测试；
- 是否有旧实现或未接通分支。

发现“定义存在但调用链没接通”时，必须明确写成当前缺口，不能因为存在函数/Skill/类型就判断能力已经完成。

## 4. 完整性原则

调研目标是覆盖当前范围内所有重要事实和独立缺口，禁止人为截断为 Top 3 / Top 5。

可以为了可读性分章节，但不能省略：

- 关键入口；
- 核心数据；
- 主要调用链；
- 状态与持久化；
- 外部依赖；
- 输出合同；
- 失败/降级/恢复；
- 重要测试边界；
- 已知未完成能力；
- 真实性边界。
