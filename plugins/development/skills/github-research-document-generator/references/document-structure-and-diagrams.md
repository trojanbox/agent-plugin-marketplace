# 调研文档结构、图示与内容写法

仅在调研范围较大、需要结构化长文或 Mermaid 图示时读取。

# 四、文档组织：Wiki 风格 + 循序渐进

完整模板使用主 `SKILL.md` 在持久化分支中声明的调研文档模板。

推荐正文顺序：

1. 标题与元数据；
2. 摘要 / 结论；
3. 背景与调研问题；
4. 范围与非目标；
5. 关键概念与术语；
6. 系统/模块全景；
7. 入口与上游输入；
8. 核心数据结构；
9. 主流程；
10. 模块/Agent/服务逐项实现；
11. 外部依赖；
12. 输出合同；
13. 状态、持久化、失败与恢复；
14. 测试与可验证性；
15. 当前能力与缺口；
16. 结论；
17. 真实性边界；
18. 参考文献与证据。

不适用的章节可以省略，但必须说明为什么不适用。复杂系统调研不能为了缩短篇幅省略关键层。

## Wiki 风格可读性要求

- 首次出现的内部术语先解释再使用；
- 长章节先给“本节回答什么”；
- 表格适合做对照和枚举，流程行为用图；
- 每个模块先写职责，再写输入，再写处理，再写输出，再写边界；
- 当前实现、需求定义、推断、差距 必须明确区分；
- 不把未来建议混入当前实现描述；
- 同一个事实只定义一次，后文通过链接/章节引用复用，避免多处产生矛盾版本。

# 五、图文规则：优先使用 Mermaid

## 1. 基本原则

只要 Mermaid 能够准确表达，就必须使用 Mermaid。不能为了省事直接使用 ASCII / Unicode 文本图。

常见映射：

| 内容 | Mermaid 类型 |
|---|---|
| 主流程、条件分支、数据流 | `flowchart` |
| 前端/后端/服务/Provider 调用顺序 | `sequenceDiagram` |
| 状态和状态迁移 | `stateDiagram-v2` |
| 表/实体关系 | `erDiagram` |
| 模块/类静态关系 | `classDiagram` |
| 阶段依赖 | `flowchart` / `timeline`（GitHub 支持时） |

## 2. 强制画图条件

满足任一条件时至少需要对应图：

- 3 个及以上连续处理步骤：Flowchart；
- 跨模块/跨服务：Flowchart + Sequence Diagram；
- 异步 Job / Workflow / Agent orchestration：Flowchart + Sequence Diagram；
- 状态推进/恢复：State Diagram 或带失败路径的 Flowchart；
- 数据实体/表关系是理解重点：ER Diagram；
- 当前实现与目标方案同时存在：分别绘制当前实现 / 目标方案，禁止混图。

## 3. 图也必须有证据

Mermaid 节点里不强行塞长引用编号，图下必须增加证据映射，例如：

```markdown
> 图 2 证据：入口 A→B [3]；B→C [5][6]；失败分支 C→D [9]。
```

图中每个有业务意义的节点和边都必须能够映射到至少一个需求或源码引用。

## 4. Mermaid 不适合时

只有以下情况允许使用其他表达：

- Mermaid 会扭曲真实空间布局；
- 需要展示真实 UI/截图；
- 需要展示像素、图像、复杂统计图；
- 需要保持终端/协议字节布局；
- 目标 Markdown 载体无法正确渲染所需 Mermaid 语法。

退化顺序：

1. Markdown 表格；
2. 用户提供的真实截图/图片；
3. 必要的文本图；
4. 其他图形。

必须简短说明为什么 Mermaid 不合适。

# 六、各类内容的写法

## 1. 模块 / Agent / 服务

每一项固定回答：

1. 主要做什么；
2. 谁调用它；
3. 接收什么输入；
4. 关键参数来自哪里；
5. 内部执行步骤；
6. 调用哪些依赖；
7. 输出什么；
8. 如何失败/降级；
9. 当前限制/未实现能力；
10. 证据。

事实表建议：

```markdown
| 项目 | 当前实现 | 证据 |
|---|---|---|
| 输入 | `AnalysisBaselineV2` | [12][13] |
| 超时 | 30 秒 | [19] |
```

## 2. API

必须覆盖：

- route/method；
- request schema；
- response schema；
- auth/guard；
- 状态码；
- 业务副作用；
- 异步/SSE 语义；
- 错误；
- 消费者；
- 测试。

## 3. 数据/状态

必须覆盖：

- schema/type；
- owner；
- producer；
- consumer；
- persistence；
- lifecycle；
- recovery；
- consistency/idempotency；
- 旧数据/兼容性（适用时）。

## 4. 缺口

缺口只能来自证据对照：

```text
需求/Skill/合同定义了 X [需求引用]
+
当前源码只实现 Y [源码引用]
=
差距：X 的 Z 部分尚未闭环
```

不得仅凭“感觉应该有”创建差距项。
