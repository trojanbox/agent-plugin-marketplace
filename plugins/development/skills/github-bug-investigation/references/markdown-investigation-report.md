# 正式 Markdown 缺陷调查报告合同（按需加载）

仅当 `github-bug-investigation` 的 `formal_markdown_report` 模式触发时使用。**默认分析模式不得加载本文件，也不得为此自动创建文件。** 本文件规定报告交付格式和审计门禁；实际缺陷类型、严重级别、复杂度、Issue Gate 仍以主 SKILL.md 为准。

## 一、报告目标与输入

- 目标：交付一份独立可读、可转发、供其他研发人员复核的 **真实 `.md` 文件**，兼顾业务现象与技术证据；读者无需回看聊天记录。
- 用户已给出上一轮完整调查时，先核对当前还能访问的证据及有效约束，再整理报告；不为写文档机械重跑测试、拉仓库或重做一遍调查。
- 标明检查对象：项目/仓库、分支、Commit/Snapshot、调查日期、运行环境、用户提供的复现条件。只有工具或输入确认时才填写精确值；未知写「未取得」，不补虚构数字。
- 将“代码缺陷已确认”和“这次用户事故由该缺陷导致”分别给出结论；缺少当次输入、日志或产物关联证据时，后者只能列为待验证。
- 以最新可用的源码、真实执行输出、日志/测试证据为依据；历史文档和聊天只作为线索。不能访问源码时明确 `source_unavailable`，不能用猜测的路径/行号/代码、假测试结果冒充证据。
- 如果要求报告时尚未形成根因，仍可交付**进行中调查报告**；状态标注 `hypothesis` / `blocked`，写明下次如何证伪，不把推断冻结成方案。

## 二、推荐章节（按内容裁剪，保留有信息量的标题）

```markdown
# {项目/模块}｜{可见故障} 问题调查报告
> 调查基线：{仓库/分支/Commit、日期、环境或「未确认」}
> 调查状态：{confirmed / hypothesis / blocked}；分类：{PRODUCTION_BUG 等}

## 1. 一页摘要
- 用户遇到了什么；影响与严重级别；已确认的结论和未确认事项。
- 给非开发人员的通俗解释，避免假定读者知道前文对话。

## 2. 问题场景与边界
- 触发条件、复现步骤、预期/实际行为、影响/未影响对象。
- 明确哪些材料/环境检查过，哪些尚未检查。

## 3. 现有实现与调用链
- 入口 → 状态/约束 → 生产者/消费者 → 持久化/外部边界 → 故障点 → 用户现象。
- 复杂调用链可用 Mermaid；有证据才绘制边/节点。

## 4. 缺陷逐项分析
### 缺陷 A（分类、优先级、根因状态）
- 故障机制、精确触发前提、最小复现输入/输出、影响范围、根因/假设。
- 分开说明代码级复现结果和具体事故归因状态，避免将相关代码风险误写成已确认的线上事件原因。
- 多个独立根因分别写，禁止把某次实际事故同时归因于多个已验证代码缺口。

## 5. 可追溯源码与运行证据
| 证据 | 文件路径及行号 / 日志来源 | 证明什么 | 边界 |
| --- | --- | --- | --- |

## 6. 复现与验证
- 真实执行命令、工作环境、输入、实际结果；未执行的操作标「建议验证」。
- 单元/集成/真实环境证据分开，现有测试通过不代表缺陷已解决。

## 7. 永久解决方向及可能副作用
- 修复责任边界、应保持的不变量、需复核的消费者/数据。
- 非平凡方案记录已检查的影响面、关键反例、仍存活的风险；低风险局部修复按需简化。
- 临时缓解措施必须写退出条件，不替代正式方案。

## 8. 回归范围与验收标准
- 原始故障回归、邻近行为、反向/失败路径、关键非目标对象。
- 用可观察且可测量的结果表述；未执行的验收不称通过。

## 9. 结论与后续决策
- confirmed/hypothesis/blocked；P0–P3；S/M/L；Patch Fast Lane eligible/blocked。
- 剩余待证伪假设、最小下一步证据、不可越过的工作边界。
```

可根据任务增加结构对照表、时间线、数据流/状态图、附录。章节标题可针对项目改名；不强制凑字数、无关图表、所有可选章节。

## 三、证据分级与引用纪律

- `verified_fact`：可复查的当前源码、真实测试/日志/工具结果；指出**相对项目根目录的准确路径 + 行号范围 + 方法/变量**，以及证据实际支持的最小结论。文件/行号可能变化时同时给标识符。
- `inference`：基于已验证事实的合理推导，写清前提和可能例外。
- `hypothesis`：待验证竞争原因。每项说明支持事实、能反驳它的观察以及需要什么下一条证据。
- `unknown`：资料不可用、无法访问日志/源码、未做运行验证；不能默认为否、已经修复、或者生产稳定复现。
- 代码片段来自真实源码时标明位置，示意代码需明确标「简化示意」，避免误导读者认为代码逐字来自仓库。不要编造 GitHub 链接、commit、line-anchor、Issue、测试输出、数据指标。
- 复现可拆为「已执行」和「建议测试」。命令执行失败也记录真实错误和局限。只读代码核查不能冒称线上事故取证；函数级复现不能冒称 E2E。
- 如果报告讨论多个缺陷，分别标注根因状态、影响、证据与建议；说明它们之间是否有经过验证的因果关系。

## 四、交付和完整性 Gate

1. 用宿主当前可用的文件工具生成**实际 UTF-8 Markdown 文件**，优先放在用户可访问的输出目录；文件名表达项目、主题，例如 `vcp-page-library-bug-investigation.md`。不要默认修改业务仓库或提交报告到 Git；除非用户明确要求。
2. 生成后检查文件确实存在、非空、可读取，标题/章节/代码围栏/表格/Mermaid 围栏闭合；如环境允许，做简短 Markdown 格式检查。完成验证前绝不宣称文件已交付。
3. 用户可直接下载时给出工具**验证过的原样路径**和链接；对于不能通过当前会话访问的外部设备路径，使用实际可访问的发布/传输能力，不能凭目录名虚构 `sandbox:/mnt/data/...` 链接。
4. 无写入/发布能力、验证失败时说明具体限制，回退为可直接复制的完整 Markdown 文本；不可只给空文件名或占位下载链接。
5. 报告自包含，不用「如上所述」「见前一轮讨论」代替关键事实；保留必要引用路径/证据，不能把真正有出处的报告写成脱离来源的纯观点。
6. 过滤凭据、私有 Token、用户隐私、敏感日志和内部认证 URL；例子使用占位数据，报告不贴未经处理的完整敏感响应。
7. 文件交付**不自动触发 Issue、新版结论或 Git 写入**。同时被明确要求创建 Issue 时，按主 Skill 的 Issue Gate 与 `github/github-issue-manager` 流程单独操作，取得真实远端结果才能声称完成。

## 五、完成前快速核对

- [ ] 用户提出的每个缺陷都有症状、证据、根因状态、影响和永久解决方向。
- [ ] 分支/Commit/环境、源码引用、执行命令和测试结果全部真实可追溯。
- [ ] 图表与源码证据一致；示意与真实事实明确区分。
- [ ] 普通业务读者看得懂，研发人员可沿路径复核，未决事项与验收条件独立完整。
- [ ] 已实际创建/验证/提供 `.md` 文件；受限时如实回退正文。
- [ ] 未触发未经授权的 Issue、代码修改或 Git 写入。
