# Bug 根因质量门禁（按需加载）

仅供 `development/github-bug-investigation` 的**复杂调查/非平凡修复方向**使用。适用场景：具体线上事故归因、多候选根因、跨层调用、共享消费者、模型/提示词输入输出、数据写入、迁移/兼容或潜在高影响副作用。简单局部 Bug 只执行主 `SKILL.md` 的基本证据要求；不为满足模板扩大调查范围，也不自动运行 E2E 或执行修改。分类、P0–P3、S/M/L、Issue 与 Patch Fast Lane 的最终规则继续由主 Skill 和 Development 共享规范负责。

## 1. 一手证据与真实调查基线

- 先明确用户描述的**当前故障与期望**、仓库/分支/Commit（或工件版本）、受影响入口、可取得的运行环境/时间范围。历史聊天、旧报告、旧缺陷、过时截图只作为调查线索；能读取当前代码时，应重新确认相应实现是否已变更。
- 配置文件值、环境变量默认值、发布包版本和运行进程真正加载的值属于不同证据层；跨配置加载、序列化、队列、RPC 或部署边界时，沿数据流检查实际消费点。不能把源码的“可能执行”直接写成那次线上请求“已经执行”。
- 选择能直接支持所提结论的**最小一手证据**：调用路径和真实输入输出、目标运行 Trace/日志、关键状态或持久化记录、运行时模型请求/最终组装提示词、具体源码及单元/函数级复现。仅使用已获授权且有权限访问的材料，日志/报告去除凭据与隐私。
- AI 问题按失效点区分：上游输入、提示词装配、schema/工具协议、模型响应、后续确定性加工、落盘/展示。**模板提示词不等于最终发送给模型的提示词**；缺少真实调用证据时不得将某句 Prompt 认定为当次删改的已确认原因。

## 2. 两种“确认”不得混为一谈

| 结论对象 | 达到 confirmed 所需证据 | 证据不足时怎么说 |
| --- | --- | --- |
| **代码级缺陷** | 当前代码违反已确认行为契约，并有可追溯的具体执行路径、反例或最小复现证明 | 指出真实风险及触发前提；根因仍有竞争假设就标 `hypothesis` |
| **用户本次事故归因** | 这一次事件的输入/状态/Trace/产物与缺陷触发链相联系，并能排除足以改变结论的主要替代原因 | “已确认代码存在缺陷 A；本次事故是否由 A 触发未证实”，不能用相关性冒充因果 |

- 可以出现“代码级 confirmed，事故级 unknown/hypothesis”的组合；不用为拿不到线上 Trace 而否认已复现的代码缺陷，也不能因此宣称某位用户的事故已经查明。
- 函数级复现不等于完整线上复现；其他样本的统计频率不能证明某个指定个案。需要时间对齐时说明实际时间基准和时区，避免跨来源误关联。

## 3. 竞争假设与证伪

在真实分叉处记录**最少足以改变决策**的候选假设，按下表填写，避免无依据地列十几个“可能是”：

| 候选根因 | 支持证据 | 预期可观测结果 | 能推翻它的观察 | 最小下一条证据 |
| --- | --- | --- | --- | --- |
| H1 | 当前已见的一手事实 | 如果 H1 为真，应该看到什么 | 看到什么则不能继续采用 H1 | 最小安全只读检查 |
| H2（如有） | 与 H1 的关键区别 | 如何与 H1 分离 | 什么反例会否定 H2 | 真实日志/复现/边界数据 |

- 用新证据逐个更新状态，明确 `verified_fact / inference / hypothesis / unknown`，区分“证明了函数可失败”和“证明了事故由此引起”。
- **允许提前结束调查**：证据缺失、权限不允许、环境不可用、版本对应不上、无继续区分价值，记录 `blocked` 或 `hypothesis`，交付已确认事实、不能冻结的判断及一条最有信息增益的后续证据。不得按猜测补全链路，也不得为了凑确定结论擅自修改系统。

## 4. 永久方案前的影响面与对抗审查

只在实际传播风险存在时扩展检查，使用**当前源码**收集证据：

1. **调查影响面**：修改点的实际调用方和消费者、共享封装/分支、状态与持久化、外部合同、失败/恢复路径、已有测试；区分真实使用者与未被使用的过时层。列出已检查与未检查的范围。
2. **主动攻击方案**：尝试构造至少一个会使修复无效、使原本成功流程失败或改变数据语义的反例；检验路径、输入、环境、并发/恢复条件的适用性。对共享函数核对消费者依赖的错误传播、重试和兜底；不替不存在的场景制造工程复杂度。
3. **收敛而非反复重写**：反例成立则修正方案及其**理由**，必要时重新核查新方案；找不到有证据的反例可写“已检查 X，未发现”，不能写“绝无副作用”。旧方案碰巧正确、根因解释错误时，仍应纠正解释。
4. **停在授权边界**：跨服务职责、状态所有权、API/数据合同、权限或用户可见行为需要新决策时标明 `DECISION_REQUIRED`，不要擅自冻结方案、替用户选方案或继续设计未经确认的新能力。临时止损必须与永久修复分开，并声明退出条件。

## 5. 验证必须说明“到哪一层”

| 证据层级 | 能支持的结论 | 不能声称 |
| --- | --- | --- |
| 源码/静态检查 | 存在指定控制流、边界或潜在缺口 | 特定线上运行必然经过该分支 |
| 函数级实际复现 | 对已给定输入可出现该故障 | 已定位指定用户个案，或真实页面已恢复 |
| Unit / Integration | 已执行范围内的行为或模块协作满足断言 | 未覆盖的完整业务路径必然正确 |
| 真实消费终点/真实环境 | 在所运行的上下文中，持久化/实际报文/页面/用户能力是否恢复 | 未运行环境、其它版本或全部用户场景也已修复 |

- 只记录**实际执行**的命令、退出结果、有效断言/用例数和未覆盖边界；跳过、无匹配、截断、错误码被管道吞掉等情况不得冒充通过。
- 需要验证的修复不等于本 Skill 已实施修复。若当前只调查，就给明确的**后续验收条件**；复杂 E2E、部署、外部环境或真实模型调用遵守用户授权、项目规则和实际工具能力，不机械要求运行。
- 验收必须包括原始失败、典型正确路径、关键非目标对象与确有必要的失败恢复分支。用户故障是否恢复，必须通过对应的消费端/最终产物验证才能宣布。

## 6. 简洁交付方式与停止条件

调查结论优先交付：**症状与范围 → 已证实的代码根因 → 本次事故归因状态 → 存活的竞争假设与关键证据 → 经反例审查的永久修复方向 → 影响面/验收边界**。缺的证据只列会改变结论的内容。

- 局部简单问题不必填写完整假设表或绘制复杂调用链。
- 有多个独立缺陷时分别给出级别、证据与结论；不能把各自可复现性相加，当作它们共同导致用户事故的证据。
- 未找到已实现目标能力时明确 `NOT_IMPLEMENTED`；合同未决定写 `CONTRACT_UNDECIDED`，不得顺手构造新功能设计。
- 调查、报告、Issue、Patch 的文件/远端写入授权继续由主 `SKILL.md` 控制；本参考不创造额外写权限。
